## 0. Главное за минуту

1. Проект — SPH-решатель (C++17, OpenMP) с двумя видами «вычислительных структур»:
   **Solid** (SPH-частицы твёрдого тела, 1D/2D/3D) и **Fiber** (нити как цепочки бусин,
   только 3D). Они взаимодействуют пятью видами пар (§4).
2. Существующие e2e-кейсы **BC2** и **BC6** — осесимметричные (2D), **без нитей**, удар по
   керамике B4C, сверка с приборным эталоном (кривая скорости тыльной поверхности).
   Они задают **шаблон e2e-теста** в этом проекте (§2–§3).
3. e2e-кейсов **с нитями нет вообще**. Есть два **демо** (не тесты): снаряд против креста из
   двух нитей и против сети из 4 слоёв (§5). Эталона для нитей нет — ни
   экспериментального, ни расчётного.
4. **Контактная физика нитей сейчас численно неверна** (§6): Fiber-Fiber-Contact считает одно
   пересечение нитей несколькими primitives и рождает энергию. Проверено: в демо
   «4 слоя» суммарная энергия растёт в 2.5 раза (pierce) и в 18 раз (stop). Четыре
   задачи на исправление **описаны, но не внедрены** (§6.2). Любой e2e с нитями, который
   сверяет числа, до их внедрения закрепит ошибку.
5. Расчёт **не воспроизводим побитно** при OpenMP с несколькими потоками; итог «сколько
   связей порвалось» и «остановился ли снаряд» меняется от прогона к прогону (§7.4).
6. Чего в коде нет, а любой e2e на нитях потребует: монитор/лог по нитям, энергобаланс,
   читалка кадров нитей на C++ (§7).

## 1. Проект в общих чертах

### 1.1. Что считает

SPH (smoothed particle hydrodynamics) для ударных задач. Материалы — реестр `itype`
(`include/materials.hpp`): 3 тантал, 4 алюминий, 5 LiF, 6 полиуретан 160, 7 полиуретан 320,
8 полиуретан 626, 9 PMMA, 10 B4C (модель прочности JH-2), 11 Al2O3. Плотность частицы
берётся из описания геометрии (`rho_0[i] = rho[i]` при построении), не из таблицы.

Ядро — кубический сплайн, `h = 1.3·(m/ρ)^(1/dim)` при `sle = 1` (пересчитывается на первом
же шаге, стартовое `2·Δx` — формальность). Схема времени — предиктор-корректор (PC) «в
варианте проекта»; есть ещё явный Эйлер (только для тестов сходимости).

### 1.2. Размерность — константа компиляции

`dim` — `constexpr` из `SPH_DIM` (CMake, по умолчанию 1; ADR-002). Следствие: **каждая цель
сборки с другой размерностью компилирует собственные копии `src/*.cpp`**
(`${SPH_PIPELINE_SOURCES}`). Эталонные кейсы BC2/BC6 — `SPH_DIM=2` + `axis_sim = true`;
всё, что связано с нитями — `SPH_DIM=3`. Нити при `dim != 3` запрещены
(`fiber::check_fiber_requires_dim3()`).

### 1.3. Конвейер одного шага

Единственная реализация цикла — `detail::run_time_integration<Solver>` в
`src/time_integration.cpp` (две публичные перегрузки `time_integration(...)`: для
`ParticleSystem&` и для `fiber::Model&` — обёртки над ней):

```
solver.predict()                      предиктор по f^{n-1}
single_step -> Solid RHS              Solid-SPH + Solid-Solid-Contact
update_smoothing_length               (sle=1) пересчёт h -- ДО расчёта dt, намеренно
[если есть нити]
  Fiber-Bond                          растяжение связей
  Fiber-Fiber-Contact                 контакт нить-нить
  Fiber-Solid-Contact                 контакт нить-тело (вклад и в Fiber, и в Solid)
dt = min(CFL по Solid, dt контакта Solid, dt связей/контактов нитей)
solver.advance()                      корректор на полный шаг
apply_material_strength               Мизес / JH-2
run_fiber_topology_postprocessing     разрыв связей l > l_break
if (time >= next_output_time): output() + fiber_output()   // каждые save_t
time += dt;  дописать строку в log.txt
RunGuard::should_stop(...)
```

Вывод кадров: `output()` пишет `sph_output_<ts>.txt`, `fiber_output()` — `fiber_output_<ts>.txt`,
**номер `<ts>` — счётчик шагов, у пары кадров общий**. Первый кадр — шаг 1, `time = 0`.
`log.txt` — одна строка на шаг: `время  v_axis[moni_particle]  itype` (осевая компонента
**Solid**-частицы `cfg.moni_particle`; нитей в нём нет).

Всё пишется **в текущий рабочий каталог процесса** жёстко зашитыми именами (`log.txt`,
`sph_gp.csv`, `sph_output_*`, `fiber_output_*`). Поэтому e2e-тесты и демо делают `chdir`
в отдельный каталог прогона.

### 1.4. Сборка и запуск (проверено)

```bash
cmake -S . -B <build> -DCMAKE_BUILD_TYPE=Release
cmake --build <build> -j8 --target demo_fiber_layers demo_fiber_net test_e2e_fiber_contact test_e2e_fiber_solid
```

Собирается на macOS без правок (Apple Clang + libomp). Каталог `build/` в рабочем дереве
**устарел** (в нём цели `test_e2e_bc1`, `test_flat_grid`, `test_pair_graph`, которых в
проекте больше нет) — собирать в новый каталог. На Windows бинари называются `*.exe`;
в старых README путь `./build/demo_fiber_layers.exe` — следствие этого.

`ctest`: быстрый набор — `ctest --test-dir build -E full`; медленные полные прогоны BC2/BC6
регистрируются только при `-DSPH_E2E_SLOW_TESTS=ON` (`ctest -L slow`).

Python-скрипты демо требуют `numpy` и `matplotlib`; **ни в одном из трёх python3 на
машине их нет**. Ставить в изолированное окружение (`uv run --with numpy ...`).

## 2. Эталонные e2e-кейсы: что именно моделируют

Оба — осесимметричные (`dim = 2`, `axis_sim = true`, координаты `x[0] = r`, `x[1] = z`),
плосковолновые ударные опыты на B4C; величина сверки — **осевая скорость `v_z` частицы
на тыльной поверхности образца, на оси**. Полные постановки: `contact/06-e2e-case.md` (BC2),
`contact/06-e2e-bc6.md` (BC6); численная методика — `contact/05-e2e-math.md`.

### 2.1. BC2 — удар по карбиду бора (Grady & Moody, SAND96-0551, опыт BC2/CE6)

Сборка из четырёх тел встык вдоль оси `z`, единицы — мм:

| № | Роль | Материал, `itype` | ρ₀, кг/м³ | `v_z`, м/с | Толщина | Радиус |
|---|---|---|---|---|---|---|
| 1 | подложка | полиуретан 626, 8 | 640 | 2210 | 6.000 | 43.75 |
| 2 | керамика летящая | B4C, 10 | 2517 | 2210 | 3.917 | 34.60 |
| 3 | керамика неподвижная | B4C, 10 | 2517 | 0 | 9.033 | 34.60 |
| 4 | окно | LiF, 5 | 2640 | 0 | 25.400 | 25.40 |

- Узлы по центрам ячеек, шаг подгоняется под толщину слоя: `n = max(1, round(L/Δx))`,
  `d = L/n`. Толщина слоя воспроизводится **точно**. Зазоров между телами нет (раньше
  были `Δx/4Δx/Δx` — сняты: статья их не подтверждает, и зазор «в долях шага» меняет
  постановку при смене разрешения).
- Δx полного режима 0.2 мм → 33 944 частицы; smoke 0.8 мм → 2 152. Монитор —
  тыльный слой тела 3 на оси (индекс 10 074 / 665), ищется **геометрически**, не литералом.
- Конфиг решателя: `pa_sph = 2, nnps = 2, sle = 1, skf = 1, CFL = 0.1, epsilon (XSPH) =
  0.25, alpha = beta = 1, etq = 0.01`, `t_total = 3.5e-6`, искусственная вязкость да,
  XSPH да.
- Сверка — **по форме кривой**, а не по значениям в общем времени: у эталона начало
  отсчёта произвольно (статья прямо так говорит). Признаки: пик, моменты 10/50/90 % на
  переднем фронте, спад до 70 %; кривые совмещаются по `t_50` фронта; сравниваются
  безразмерные отношения. Ворота **намеренно грубые**: отношение пика `[0.5; 2.0]`,
  отношение длительности фронта `[1/3; 3]`.
- Известные расхождения с опытом (описаны в `06-e2e-case.md` §5): пик занижен на треть
  (0.659), спад растянут вдвое (2.5), фронт совпал (1.017). Причины — гипотезы
  (размазанная граница не даёт импедансного усиления, численная диссипация разгрузки).
- **Контакт B4C↔B4C (тела 2 и 3) контактным алгоритмом не виден**: критерий пары —
  «разные `body`», а у обоих тел `itype = 10`. Тест фиксирует это как ограничение.

### 2.2. BC6 — откольный опыт на B4C

| № | Роль | Материал, `itype` | ρ₀ | `v_z`, м/с | Толщина, мм | Радиус, мм |
|---|---|---|---|---|---|---|
| 1 | подложка | пена, 6 | 160 | 913 | 8.000 | 43.75 |
| 2 | ударник | PMMA, 9 | 1186 | 913 | 2.004 | 43.75 |
| 3 | образец | B4C, 10 | 2506 | 0 | 10.526 | 38.05 |
| 4 | окно | PMMA, 9 | 1186 | 0 | 24.200 | 38.05 |

- Δx = 0.2 мм → 44 638 частиц; smoke 0.8 мм → 2 930. `t_total` = 4.3 мкс. Сборка встык,
  все границы — между разными материалами, контакт работает на всех трёх.
- **Два монитора**: на оси и контрольный на `r = 12.5 мм`. Профиль — не плато, а
  **убывающая лесенка** из трёх ступеней (170 → 141 → 115 м/с) с двумя провалами
  (114.9 м/с при +0.90 мкс, 105.8 м/с при +1.76 мкс от фронта). Проверки: приход
  фронта `0.739 ± 0.05` мкс по 50 %, плато 1 в `[170; 190]`, отношение ступеней
  `0.82 ± 0.02`, период лесенки `0.88 ± 0.15` мкс, `D = 0` во всём образце до прихода
  разгрузки, контакт обнаружен на всех трёх границах.
- Текущий результат (тип контакта 0): плато 182.8 м/с (эталон 171.8), период 0.917 мкс
  (0.899), отношение ступеней 0.703 (0.823), второй провал **не найден**, возврата после
  первого нет, JH-2 даёт `D = 1` в угловой частице уже при 0.054 мкс (краевой артефакт
  SPH) — **единственный падающий check** BC6, оставлен жёстким намеренно.
- Эталон — приборная запись (`tests/data/bc6_reference.txt`, 236 точек). Передний фронт
  в нём оцифрован «облаком», поэтому ворота по длительности фронта для BC6 выключены.
- Важный урок кейса: **штраф контакта на равновесном расстоянии обязан быть ровно нулевым**
  (радиус частицы `R = ½(m/ρ)^(1/dim)` → при `m = ρ₀Δx^dim` сумма радиусов на границе ровно `Δx`,
  перекрытие 0, пара не засчитывается) — иначе сборка получает импульс ~10⁴ м/с на
  первом шаге. Это проверяется операционно и наблюдательно.

### 2.3. Что эти кейсы дали проекту (важно для мотивации нового)

- Ловят кратные поломки конвейера (отказ шага, NaN, обрыв прогона), а не процентные
  изменения — для процентных есть регрессия (§3.6).
- Нашли реальные дефекты: осесимметричный член неразрывности в цикле по парам, знак
  в производной Яуманна, дребезг импульсного контакта (тип 3), `std::isspace(char)` на
  Windows. Ценность e2e — в том, что он работает на реальной постановке.

### 3.2. Принципы, которые проект выработал (ТЗ стоит их наследовать)

1. **Числа кейса — в одном заголовке `*_case.hpp`**, геометрия строится функцией, число
   частиц и положение мониторов выводятся из формул и проверяются.
2. **Параметры решателя — в файле формата боевого конфига**, а не выставляются полями
   мимо парсера.
3. **Один прогон — один вариант** (например, один тип контакта). Обрыв одного не скрывает
   остальные, а в отчёте `ctest` виновник назван по имени. Сводный график собирается из
   выгрузок отдельных прогонов (`--emit-curve`, `--plot-from`, `--emit-plot`).
4. **Два режима.** `smoke` (по умолчанию, секунды, грубая сетка, укороченное время; в
   `ctest` всегда) проверяет живучесть конвейера; `--full` (минуты; регистрируется только
   при `-DSPH_E2E_SLOW_TESTS=ON`, метка `slow`) проверяет физику. Проверки, которые в
   smoke вырождены (волна не дошла до монитора), **пропускаются с явным предупреждением**,
   а не тихо проходят.
5. **Без побочных эффектов**: прогон в временном каталоге (`ScopedWorkDir`), после —
   проверка, что рабочий каталог не изменился. Вывод конвейера глушится
   (`ScopedSilence`). Флаг `--keep-workdir` оставляет каталог для разбора обрыва.
6. **Сторож `RunGuard`**: бюджет по стенным часам (`--time-limit=СЕК`) + детектор застоя
   (коллапс `dt`) + `set_step_limit` для останова по числу шагов. Различает «не успел»
   (WallClock), «дефект» (Stalled) и штатный останов (StepLimit).
7. **Обязательные проверки живучести на каждом кадре**: нет NaN/Inf в `x, v, ρ, p`,
   `ρ > 0`, `m > 0`; расчёт дошёл до `t_total`; `dt` не схлопнулся (`dt_first/dt_min`).
8. **Сверка формы, не времени**, если у эталона произвольный ноль времени. Допуски —
   по разрешению эталона, не жёстче (у BC6 приборное разрешение ≈ 3 м/с).
9. **Самопроверка компаратора** на данных эталона и на синтетике (сдвиг по времени не
   меняет отношения; ×3 по амплитуде проваливает амплитудные ворота, не трогая фронт;
   растяжение по времени — наоборот). Без неё красный/зелёный тест не доказывает ничего.
10. **Эталон не генерируется тестом молча.** Для регрессионного эталона — осознанная
    команда владельца и признание расчёта корректным **до** записи эталона (иначе тест
    закрепит ошибку; именно поэтому у BC2 полный эталон «намеренно не сгенерирован»).
11. **Отрицательный результат — это результат.** Постановка BC6 прямо называет «нет

## 4. Нити: модель и интерфейсы

Полная спецификация — `fiber/SPH.md`; план и решения Р1–Р10 — `fiber/PLAN.md`; архитектура
— `docs/04-explanation/decisions/adr-008-rhs-architecture-fiber.md`.

### 4.1. Модель (по Meyer, с отступлениями проекта)

Нить — цепочка бусин. Масса бусины постоянна: `m_i = ρ_f·A·(l⁰_{i−1,i} + l⁰_{i,i+1})/2`,
`A = πd²/4`; у конца нити — прилежащий сегмент один (без деления пополам повторно).

| Взаимодействие | Физика | Куда вклад |
|---|---|---|
| **Fiber-Bond** | `F = E·A·max(l/l⁰ − 1, 0)·n` — **только растяжение, изгиба нет** | Fiber |
| **Разрыв** (Postprocessing, после `advance`) | связь удаляется, если `l > l_break = (1+ε_b)·l⁰`; у обеих сторон `next/prev = −1`, оторванной части — **новый `object_id`**, `topology.version++` | топология |
| **Fiber-Fiber-Contact** | Герц: `F = (4/3)·E*·R*·(d−D)^{3/2}`, `E* = E/(2(1−ν²))`, `R* = √(d/4)`; геометрия по локальным осям нитей (4 случая: Surface-Surface/-End/End-Surface/End-End), сила распределяется по топологическим соседям весами Meyer; `D` — расстояние между осями; пары только разных `object_id` | Fiber (обе) |
| **Fiber-Solid-Contact** | сегмент нити `(a,b)` против Solid-частицы `s`: ближайшая точка `q = a + λ(b−a)`, `δ = r_f + r_s^contact − D`, `F = K_fs·δ^{3/2}`, `K_fs = (4/3)E*_fs√R*_fs`; `E_s, ν_s` Solid выводятся из `K` и `G`; `r_s^contact = ½(m/max(ρ,ρ₀))^{1/dim}` | Fiber **и** Solid |
| **Solid-Solid-Contact** | штрафные силы типов 1–3 (`contact_force_type`), пара — `body[i] != body[j]` | Solid |

Трение между нитями — явный Кулон без памяти контакта (`mu_ff`, 7-е необязательное поле
`MATERIAL`), есть, но **дребезжит** (§6.1). Трения Fiber-Solid в коде нет вовсе.

Шаг по времени: `dt = min(CFL по Solid, dt контакта Solid, dt связей, dt контакта нитей,
dt Fiber-Solid)`, для связей и Герца `Δt_lim = 0.8/√(k_eff/m_red)`. В демо шаг определяет
**CFL алюминия** (`≈3·10⁻⁸ с`), а не нити: `dt_bond ≈ 7.8·10⁻⁶ с` на 2.4 порядка больше.

### 4.2. Файл нитей (`SimulationConfig::fiber_file`, `fiber::load_fiber_file`)

```
# комментарий
MATERIAL <id> <E> <nu> <d> <rho> <eps_break> [mu_ff]
FIBER <material_id> <point_count>        # point_count >= 2
x y z                                    # РОВНО point_count строк, вершины ломаной в
x y z                                    # НЕНАГРУЖЕННОЙ конфигурации, вдоль нити
```

- Каждый блок `FIBER` = одна нить, `object_id` = порядковый номер блока (0, 1, …).
- `l⁰` связи — расстояние между соседними точками файла; `l_break = (1+eps_break)·l⁰`.
- Нити из файла — **только прямые отрезки между заданными точками**; провисание, натяжение
  или предварительная деформация задаются самими координатами.
- Закрепления нет. Принятый приём — **«псевдо-анкеры»**: масса концевых бусин умножается
  на 50 после загрузки (`model.fiber.mass[i] *= 50` для `prev == −1 || next == −1`).
  Анкеры за прогон сдвигаются < 0.02 мм, но это не закрепление: они двигаются и
  забирают энергию.

### 4.3. Формат кадра нитей (`fiber_output_<ts>.txt`)

```
TIME <t> STEP <itimestep> N_PARTICLES <n> N_BONDS <nb>
# id object_id material_id x y z vx vy vz
PARTICLES
<n строк>
# i j l0 l l_break elongation
BONDS
<nb строк>          # elongation = (l − l0)/l0; порванная связь просто исчезает из списка
```

Метка `TIME` — время **до** инкремента на шаге; состояние — после шага (как и у
`sph_output`). id бусины = индекс в `FiberState`, **не меняется никогда**, даже после
разрыва (меняется только `object_id`).

Кадр Solid `sph_output_<ts>.txt` в 3D: заголовок
`N Nmat M x y z vx vy vz rho p u c sigma_i e_pl D hsml sxx syy szz sxy syz sxz`, строки — частицы
(индекс с 1). Массы в кадре — колонка `M`.

### 4.4. Как собирается сцена в коде (схема из демо)

```cpp
static_assert(dim == 3);                              // цель с SPH_DIM=3
fiber::Model model;                                   // {solid, fiber, topology, materials}
ntotal = build_projectile_cube(model.solid, ...);     // sys.resize; inzializ_index(k);
                                                      // x, vx, itype, body (ОБЯЗАТЕЛЬНО), rho, rho_0, hsml, mass
fiber::load_fiber_file(net_path, model);              // парсер проекта
for (i : beads) if (prev==-1 || next==-1) mass[i] *= 50;   // анкеры
SimulationConfig cfg; cfg.apply_defaults();
cfg.fiber_file = net_path;  cfg.t_total; cfg.save_t; cfg.contact_force_type = 0; cfg.moni_particle = 0;
cfg.maxn = 1.4*ntotal; cfg.max_interaction = 100*cfg.maxn;
model.solid.resize(cfg.maxn); inzializ_index(хвост);  // запас под виртуальные частицы
for (i < ntotal) urs(cfg.mats, model.solid, i);       // начальные p, c по УРС
fs::current_path(out_dir);                            // кадры пишутся в CWD
double dt = compute_cfl_timestep(cfg, model.solid, ntotal), time = 0;
RunGuard guard(900.0, 0.0, 1);
time_integration(cfg, model, ntotal, dt, time, dx, &guard);
```

Без `sys.body[k]` не работают фильтры тела (Solid-Solid-Contact, Fiber-Solid); `body[]`
= `itype[]` в построителях проекта, из k-файла — PID.

**Не проверялось:** сцена из одних нитей без Solid-частиц (`ntotal = 0`). `compute_cfl_timestep`
при `ntotal = 0` вернёт `1e6`, `fiber_solid_contact` отдельно выходит при `ntotal == 0`,
но `log.txt` всё равно читает `sys.vx[..][moni_particle]`, а таких частиц нет.

## 6. Известные дефекты контакта нитей — обязательно учесть в ТЗ

### 6.1. Что не так (диагноз в репозитории, код не исправлен)

1. **Кратный контакт нить–нить.** Одно геометрическое пересечение учитывается несколькими
   primitives (в `test_e2e_cross_friction` — 7; тест допускает до 20). Все сводят силу Герца
   на одни и те же бусины: эффективная жёсткость узла в несколько раз выше герцевской,
   зависит от угла, радиуса поиска и шага бусин (**то есть от разрешения**); `dt_limit`
   оценивает шаг по жёсткости одной пары. Решение Р8 (PLAN.md) зафиксировало это как
   «свойство модели Meyer»; анализ показал, что это нежелательно. Источник рождения
   энергии в демо «4 слоя» локализован контрольными прогонами: без разрывов — ×6.3,
   слои с зазором 1.3·d — ×1.9, один слой (контакта нить–нить нет) — 0.98–1.06.
2. **Дребезг трения.** Явный Кулон без памяти при `μNΔt/m > |v_t|` перебрасывает скорость
   через ноль каждый шаг, трение перестаёт рассеивать энергию; схема PC усугубляет
   (знак берётся от предсказанной скорости). Трение умножается на ту же кратность.
   Разбор — `fiber/friction_chattering_analysis.md`.
3. **Fiber-Solid: потеря контакта в выпуклом изломе нити.** Правило «`t ≥ 1` и сегмент не
   последний → пропуск / `t < 0` и сегмент не первый → пропуск» отбрасывает контакт с
   обоих сегментов, если частица лежит во внешнем секторе излома. Нить проходит сквозь тело.
   При ударе сетки «узлом» это типичная ситуация.
4. Радиус поиска Fiber-Fiber/Fiber-Solid не учитывает растяжение нити сверх `l0`
   (`IMPLEMENTATION_REPORT.md` §6): при сильном растяжении контакт у стыка может быть
   пропущен.
5. Трения Fiber-Solid нет.

### 6.2. Запланированные исправления — четыре инструкции, **не внедрены**

Порядок важен (каждая следующая предполагает принятой предыдущую); HEAD содержит только сами
инструкции, коммиты «fiber: инструкции по …».

| № | Файл | Суть |
|---|---|---|
| 1 | `fiber/fiber_contact_segment_pairs.md` | primitive = пара **сегментов**, ближайшие точки с параметрами `s, t ∈ [0,1]`, правило владения → ровно один контакт на пересечение; образец — `fiber_solid_contact.hpp` |
| 2 | `fiber/fiber_solid_contact_fix.md` | владение узлом (излом нити) и радиус поиска по текущей длине |
| 3 | `fiber/fiber_friction_projection.md` | трение как **проекция на уровне скоростей**: отдельная стадия **после** вычисления `dt` (прилипание/скольжение, один `mu_ff` как статический и кинематический, импульс сохраняется) |
| 4 | `fiber/fiber_solid_friction_implementation.md` | трение Fiber-Solid той же проекцией, `mu_fs` в `FiberMaterial`, mass splitting, XSPH |

**Что это значит для нового e2e.**

- Если эксперимент **про нити**, то его числа (остановился ли снаряд, сколько связей порвалось,
  какая энергия) **зависят от этих исправлений**. ТЗ должно явно сказать одно из трёх:
  (а) эксперимент ждёт внедрения задач 1–4 и выполняется после; (б) эксперимент
  выполняется сейчас, но **гейты строятся только на инвариантах** (нет NaN, нет коллапса
  `dt`, порядок слоёв не нарушен, импульс, баланс с допуском), а числовые исходы —
  справочные (`WARN`, не падение); (в) эксперимент сам диагностирует дефект, то есть его
  цель — красный тест, фиксирующий рост энергии.
- Ожидаемое поведение после задач 1–4 **изменит** результаты существующих демо и
  сценарных тестов; `mu_ff = 0` при этом обязан остаться побитно прежним там, где
  кратность не затрагивается (инвариант из `fiber_contact.hpp`). Побитность регрессии Solid
  (14 тестов) — жёсткий инвариант.
- До исправления **энергобаланс с нитями обязан нарушаться**: если ТЗ требует сохранения
  энергии — оно требует заодно исправить контакт.

### 7.1. Чего нет в коде (а e2e на нитях потребует)

| Пробел | Следствие для ТЗ |

| **Монитора нитей нет.** `log.txt` пишет одну Solid-частицу на шаг | Измерения по нитям — только из кадров (`save_t`), не с каждого шага. Для разрешения быстрых событий (разрыв за несколько шагов) нужен малый `save_t` на окне либо **хук на шаг** (его нет: `RunGuard` вызывается раз в шаг, но не даёт состояния; правка `time_integration.cpp` запрещена по умолчанию) |
| Нет C++-парсера `fiber_output_*` (`e2e_frames.hpp` читает только Solid) | Нужна новая читалка рядом с `e2e_frames.hpp`, либо проверки в Python (как `analyze_layers.py`), но тогда это не `ctest` |
| Нет энергобаланса (ни в коде, ни в тестах нитей; у `test_e2e_3d` — для Solid) | ТЗ должно определить, **что такое полная энергия** (КЭ Solid, КЭ нитей, упругая связей, внутренняя `u` Solid, диссипация XSPH/вязкости/контакта) и допуск |
| Нет закрепления нитей (только анкеры ×50) | Граничные условия сети придётся задавать либо анкерами, либо новой функциональностью — решение за ТЗ |
| Нет изгибной жёсткости, только растяжение | Нить «ткани» не сопротивляется изгибу; провисание и складки определяются только контактом |
| Нет самоконтакта нити, нет контакта нить–нить при одинаковом `object_id` | Связанные участки одной нити не взаимодействуют; оборванные фрагменты — другой `object_id`, **контактируют** |
| Нет трения Fiber-Solid | эксперименты со скольжением нити по телу невозможны |
| Нет экспериментального эталона по нитям | ТЗ должно указать источник эталона, либо кейс без эталона (тогда — инварианты, как в `test_e2e_3d`) |
| Детерминированный режим суммирования есть (`ReduceOptions::deterministic`, по умолчанию `false`; `contributions_test` проверяет побитность при 1/2/7 потоках), но **все вызовы `reduce_contributions` в цикле идут с настройками по умолчанию** | Побитная воспроизводимость только при `OMP_NUM_THREADS=1` либо после отдельной правки цикла |

### 7.2. Сборка

- Новая цель e2e с нитями = копия блока `test_e2e_fiber_solid` в `CMakeLists.txt`:
  `add_executable(... ${SPH_PIPELINE_SOURCES})`, `SPH_DIM=3`, `-fexceptions`, OpenMP
  (на AppleClang через `SPH_APPLECLANG_OMP_*` опции), `SPH_TEST_DATA_DIR` для данных.
- Метки `ctest`: `3d` (юниты нитей, e2e нитей), `e2e`, `slow` (только с `SPH_E2E_SLOW_TESTS`),
  `regression`. Таймауты — `TIMEOUT` на тест.

### 7.3. Цена (для выбора режимов smoke/full)

По нитям (на этой машине): 216 Solid-частиц + 340 бусин ≈ 880 шагов/с при шаге, заданном
CFL алюминия (≈3·10⁻⁸ с). Это **секунды–минуты**, не десятки минут, как BC. Но шаг мал:
для `t_total ~ 1 мс` нужно десятки тысяч шагов, а кадры — сотни МБ текста (на демо —
~150 файлов на прогон).

### 7.4. Воспроизводимость

При OpenMP с несколькими потоками порядок суммирования меняется от прогона к прогону;
для BC2 (на старой, уже исправленной постановке) разница между двумя прогонами одного
бинарника росла от 1 ulp до десятков м/с за ~200 шагов (`04-e2e-test-brief.md` §10; в
`06-e2e-case.md` этого раздела уже нет, поэтому актуальный масштаб для BC2 не проверялся).
Для нитей измерено прямо: дискретные исходы (число разрывов, остановка/проскок) меняются между
запусками (см. таблицу §5.3). **Гейты на целочисленные и пороговые исходы нужны с
допусками или при `OMP_NUM_THREADS=1`.**

### 7.5. Документы, местами устаревшие (на них не опираться без проверки кода)

- `contact/05-e2e-math.md` §11–12: говорит, что зеркальные частицы у оси не генерируются и
  что монитор — радиальная `v_r` на `r ≈ 12.5 мм`; **обе фразы неверны** для текущего кода
  (зеркальные частицы живут в `include/interactions/solid_sph.hpp`, логируется осевая `v_z`).
- Все ссылки вида `src/int_force.cpp:NNN`, `src/density.cpp`, `src/virt_part.cpp`,
  `src/direct_find.cpp` в `contact/*.md` — **на удалённые/переписанные файлы** (этап Ф4).
- `contact/04-e2e-test-brief.md` — исходное ТЗ BC2; его геометрия (зазоры `Δx/4Δx/Δx`,
  34 163 частицы, монитор `12973`) **заменена** постановкой `06-e2e-case.md`.
- `fiber/DEMO_VISUALIZATION_TASK.md` §4 пишет, что `fiber_output` из `time_integration` не
  вызывается; **вызывается** (`src/time_integration.cpp:241`, коммит `3463c73`).
- `fiber/IMPLEMENTATION_REPORT.md` §4.5 «продовый `time_integration` ни разу не запускается с
  непустыми нитями» — устарело (запускают демо, но не тесты).
- **Числа BC2 расходятся между документами**: `IMPLEMENTATION_REPORT.md` §1 — пик монитора
  985.0 м/с при 1.312 мкс, 1499 шагов; `06-e2e-case.md` §5 — 868.6 м/с при 1.379 мкс, 1531
  шаг. Какое актуально, не проверялось (полный прогон BC2 ≈ 6–20 мин). Если ТЗ ссылается
  на числа BC2 — перепрогнать.
- `experiments/README.md` и старые `REPRO.md` ссылаются на Windows/Git Bash (`zip`,
  `.exe`); рабочая машина сейчас — macOS.
- `build/` в рабочем каталоге — устаревший (см. §1.4).

## 8. Что ТЗ должно решить (чек-лист для автора)

Пункты, оставленные без ответа, исполнитель решит сам — и, как показывает опыт BC2/BC6,
часть таких решений потом пересматривается.

**A. Цель эксперимента**
- Что проверяется: валидация против опыта / регрессия / инварианты / диагностика дефекта /
  демонстрация? От этого зависят допуски и то, падает ли тест при «неверной физике».
- Это `ctest`-тест (smoke + slow) или эксперимент в `experiments/` без `add_test`?
- Нужен ли **эталон**. Откуда (публикация, оцифровка, свой расчёт), в каком формате,
  у кого произвольное начало времени?

**B. Постановка**
- Геометрия (размеры в мм/м), материалы (`itype` Solid; `E, ν, d, ρ, ε_break, μ` нитей),
  начальные скорости, граничные условия, **способ закрепления нитей**.
- Число и расположение мониторов; что именно измеряется (Solid-частица, бусина нити,
  сила в связи, натяжение, число разрывов, энергия, импульс снаряда, остаточная скорость,
  глубина проникания).
- Нужно ли `contact_force_type` ≠ 0 и варианты контакта (один прогон на вариант).
- Разрешение (`Δx`, `l0`) и требование сходимости по нему.

**C. Поведение и допуски**
- Какие величины сравниваются «по форме», а какие в абсолютном времени.
- Для дискретных исходов (остановка/проскок, число разрывов): допустимый коридор или
  требование `OMP_NUM_THREADS=1`.
- Что делать с известными дефектами §6: ждать / обходить инвариантами / диагностировать.

**D. Режимы и стоимость**
- Smoke: сетка, `t_total`, что проверяется, бюджет (цель < 30 с по образцу BC); какие
  проверки в smoke пропускаются с `WARN`.
- Full: бюджет по времени, `--time-limit`, место на диске под кадры.

**E. Артефакты и документы**
- Файлы: `tests/<name>_case.hpp`, геометрия, `test_e2e_<name>.cpp`, конфиг, эталон,
  скрипты, цель CMake, метка `ctest`.
- Отчёт: постановка в духе `contact/06-e2e-*.md` (геометрия, НУ/ГУ, величина, результат,
  график, что установлено/гипотеза) и/или карточка в `experiments/` (+ `REPRO.md`).
- Визуализация: SVG-график кривой (есть `e2e_plot.hpp`) и/или анимация кадров (есть
  `animate.py`, нужен numpy/matplotlib).

**F. Инварианты, которые нельзя ломать**
- Побитная регрессия Solid: 14 тестов `ctest -L regression` без перегенерации эталонов.
- `tests/test_e2e_bc2.cpp` и `tests/test_e2e_bc6.cpp` не редактируются.
- Не менять физику взаимодействий и `src/time_integration.cpp`, **если ТЗ прямо не
  разрешает**; если требует — указать единственное допустимое изменение (как это сделано
  для вывода `fiber_output` в `DEMO_VISUALIZATION_TASK.md` §7).
- Не выдавать результат за физику, пока контакт нитей не исправлен (§6).

## 9. Рекомендуемая структура ТЗ (по образцу `contact/04-e2e-test-brief.md`)

Этот шаблон уже отработан на BC2: исполнитель шёл по нему и принимал решения по
помеченным E1–E3.

1. **Цель и источник данных** — что автоматизируется, откуда геометрия/эталон.
2. **Геометрия** — таблица тел/нитей с числами, правило раскладки, **ожидаемое число частиц и
   бусин** (как проверка), положение мониторов; явный список «дефектов исходного блока,
   обязательных к исправлению при переносе», если есть исходный код.
3. **Блокеры сборки** (размерность, опции) и принятое решение.
4. **Конфигурация решателя** — значения явно, источник (файл) и кодировка.
5. **Эталон и критерий** — что сравнивается, алгоритм (интерполяция/форма), метрики и
   допуски (цифры!), обязательные проверки живучести.
6. **Режимы прогона** — smoke/full, бюджет времени, регистрация в `ctest`.
7. **Сценарии** (варианты контакта, трения и т. п.) — по одному тесту на вариант.
8. **Технические требования** — стиль (`int main`, `failures`, `printf`), изоляция
   побочных эффектов, пути данных через `SPH_TEST_DATA_DIR`, формат вывода при падении
   (обе метрики, индекс/время максимального расхождения, значения расчёта и эталона).
9. **Порядок реализации** с отметкой, **какой шаг нельзя выполнять до решения владельца**
   (например, генерация эталона).
10. **Открытые решения** — таблица `№ | решение | рекомендация`; у каждого пункта вариант по
    умолчанию, который применится, если владелец не ответит.
11. **Статус реализации** — заполняется исполнителем: что сделано, числа, подтверждённые
    прогоном, отступления от ТЗ и почему, что тест нашёл.

Опыт подсказывает три вещи, которые стоит писать в ТЗ явно:

- **«Если это меняет число частиц / результат относительно ожидаемого — зафиксировать факт в
  отчёте и пересчитать ожидание, а не подгонять условие»** (BC2 §1.3).
- **Числа — только измеренные**, оценки помечены словом «оценка» (`experiments/README.md`).
- **Отрицательный исход допустим и должен быть описан** — не смягчать ворота, чтобы тест
  позеленел.
