## 3. `7287056` — `include/contact_force.hpp` + аналитика (M1–M12)

Это математическое ядро; самый важный файл ревью. Header-only, без зависимости от `dim`.

### 3.1 `pinball_force` (тип 1) — самое сложное место плана

- [ ] Подтвердить, что реализован вариант **D1=A**: `F = Kp·min(F1,F2)`, множитель `p`
  из буквальной (2.3) **отсутствует**. Если в коде он всё же есть — это баг относительно
  принятого решения, не относительно статьи.
- [ ] Откат при неизвестном `G` (`g_eff <= 0` или `r_eff <= 0`): ветка `F2` должна
  **исключаться из `min`**, а не участвовать со значением 0 (иначе `min(F1,0)=0` —
  ровно та ошибка, которую план разбирает в 00-audit.md §3.3). Проверить код:
  `hertz_known` вычисляется **до** `f2`, и `f = hertz_known ? min(f1,f2) : f1` —
  убедиться, что этот порядок соблюдён и не переставлен при рефакторинге.
- [ ] `hertz_active` (флаг «какая ветка доминирует») используется для выбора формулы
  `dt_limit` — герцева (`1.5*F/p`) против вязкой (`2*dt_ref/Kp`). Проверить пограничный
  случай `f1 == f2`: какая ветка выбирается и не ломает ли это непрерывность `dt_limit`
  на границе перехода (не критично для корректности, но стоит явно проверить тестом).
- [ ] `out.fn <= 0.0` — early return **до** вычисления `dt_limit`: убедиться, что при
  нулевой силе `dt_limit` остаётся `kNoLimit`, а не мусорным значением от деления на
  ноль (`k_eff` со знаменателем `g.p`, если `g.p` очень мал но положителен — проверить
  отсутствие деления на близкое к нулю значение при малом `p`).
- [ ] Формула `k_eff = 1.5 * out.fn / g.p` для герцевой ветки — свериться с производной
  `dF/dp` при `F ∝ p^{3/2}` (`dF/dp = 1.5·F/p` верно алгебраически, но проверить, что
  `out.fn` в этой точке уже включает множитель `Kp`, а не голое `f2` — иначе `k_eff`
  будет в `Kp` раз меньше нужного).
- [ ] Формула `dt_limit = kOscSafety * 2.0 * pr.dt_ref / kp` для вязкой ветки — это
  вывод, сделанный при написании плана (не из статьи), а не проверенная временем
  формула. Прогнать её через размерность и через предельные случаи (`Kp → 0`,
  `Kp` большое) отдельно, не доверять только тому, что тест M5 проходит — тест мог быть
  написан по той же (возможно неверной) формуле, которой проверяется код.

### 3.2 `swegle_force` (тип 2)

- [ ] `F1 = m_red·p/dt_ref²`, `F2 = 2·m_red·c_pair·p/(dt_ref·r)` — сверить знаменатели
  и множитель `2` с (2.7)/(2.8), включая исправленную опечатку (вторая формула
  первоисточника — это `F2`, не повторение `F1`).
- [ ] `c_pair = min(c_i, c_j)` — проверить, что передаётся в `PairProps` действительно
  минимум, а не среднее или `c_i` по умолчанию.
- [ ] `k_eff = out.fn / g.p` — корректно только если `F` линейна по `p` во **всех**
  веточных случаях (обе `F1`, `F2` линейны по `p` — да, проверить, что после `max`
  линейность сохраняется, что тривиально, но стоит явно отметить в ревью как
  не-пропущенное).

### 3.3 `impulse_force` (тип 3)

- [ ] `dt_applied` — параметр, а не `pr.dt_ref` — критично: тип 3 обязан использовать
  **применяемый** шаг, не локальный CFL. Проверить сигнатуру вызова из `ext_force.cpp`
  (см. §4) — передаётся туда именно `dt` шага интегрирования, а не что-то ещё.
- [ ] `dt_limit` не устанавливается (остаётся `kNoLimit` по умолчанию в `Result{}`) —
  проверить, что это не забытый TODO, а осознанное решение (соответствует плану).

### 3.4 Общее по файлу

- [ ] `penalty_force(type, ...)` — `switch` покрывает `Off` (default) корректно,
  никакого поведения для неизвестных `type` кроме `Result{}`.
- [ ] `kNoLimit = 1e30` — сверить с константой в `time_integration.cpp`/`buffers.hpp`,
  используемой как «нет ограничения» — если где-то в этом же коде фигурирует другое
  магическое число (например, `1e6` в `compute_cfl_timestep`, строка 15 —
  **это другая константа с другим смыслом**, не путать), убедиться, что сравнение
  `min(dt, wb.min_dt_contact)` не даёт неверный результат из-за разных порядков величин.
- [ ] Все функции `inline` — при линковке `test_contact.cpp` + `src/ext_force.cpp` в
  одну цель (см. `CMakeLists.txt`) не должно быть нарушений ODR.

### 3.5 Тесты M1–M12

- [ ] Каждый тест сравнивается с **независимо** посчитанным аналитическим значением
  (вручную выведенным числом или отдельной формулой), а не с вызовом той же функции
  под другим именем — иначе тест проверяет только «функция возвращает то, что она
  возвращает».
- [ ] M6 (откат при `G` неизвестном) — ключевой тест, отдельно проверить, что он
  действительно ловит регрессию на `min(F1, 0) = 0` (временно откатить исключение
  ветки `F2` из `min` и убедиться, что тест M6 падает — если он не падает, тест
  не покрывает то, что должен).
- [ ] Допуск `1e-12` — реалистичен для всех тестов, где есть `sqrt`/`pow(x, 1.5)`
  (Герц-ветка), а не только для линейных формул.

## 4. `a753468` — оркестратор в `ext_force` + ограничитель шага

Файлы: `include/buffers.hpp`, `include/ext_force.hpp`, `src/ext_force.cpp`,
`src/single_step.cpp`, `src/time_integration.cpp`.

### 4.1 Сигнатура и точка вызова

- [ ] Новая сигнатура `ext_force(cfg, sys, dt, ntotal, niac, pair_i, pair_j, dvxdt, wb)`
  согласована со стилем остальных силовых функций (`int_force`, `art_visc`) —
  порядок параметров, `const&` где нужно.
- [ ] Вызов из `single_step.cpp` передаёт **правильные** `dt` и `wb` — не перепутаны
  местами с другими буферами/шагами (в частности, `dt` на этой стадии конвейера —
  это шаг, использованный для интегрирования на текущей итерации, а не будущий
  `dt` после `compute_cfl_timestep`).
- [ ] `#include` в `ext_force.hpp` не создают циклическую зависимость
  (`simulation_config.hpp` → `materials.hpp`; `buffers.hpp`; `contact_force.hpp`).

### 4.2 `is_contact_pair` (реализация D2=A)

- [ ] `itype[i] > 0 && itype[j] > 0 && itype[i] != itype[j]` — проверить фактический
  код, не только план: легко случайно написать `||` вместо `&&`, или забыть проверку
  `> 0` и пропустить виртуальные частицы (`itype < 0`) в контакт.
- [ ] Комментарий об ограничении (два тела одного материала не увидят контакт)
  перенесён в код — не потерялся при реализации.

### 4.3 `pair_dt_ref` — локальный CFL-шаг пары

- [ ] Формула идентична `compute_cfl_timestep` (`time_integration.cpp:13-27`), но
  для одной частицы `k`, не для всех — сверить построчно, включая `sqrt(v2)`, а не
  `v2` напрямую (легко забыть `sqrt`).
- [ ] `pr.dt_ref = min(pair_dt_ref(i), pair_dt_ref(j))` — минимум по **обеим**
  частицам пары, не только по одной.
- [ ] `denom > 0.0 ? ... : 1e30` — что происходит, если `c[k] == 0` и `v == 0`
  одновременно (частица без скорости и без EOS-обновления `c` на первом шаге,
  до вызова `int_force`)? Проверить, вызывается ли `ext_force` **после** обновления
  `sys.c` в конвейере (план утверждает это на основании `single_step.cpp:189` до
  `205` — перепроверить, что порядок не изменился при реализации).

### 4.4 Тело контактной ветки — геометрия, направление силы, накопление

- [ ] `p = 0.5*(hsml[i]+hsml[j]) - r` — точная (2.1), не перепутаны `i`/`j`.
- [ ] `g.pdot = -dot/r` — знак: `dot = Σ dx[d]*dv[d]`, где `dx = x_i - x_j`,
  `dv = vx_i - vx_j`. При сближении (частицы движутся друг к другу) `pdot` должен
  быть **положительным** — проверить на конкретном численном примере (не только
  довериться выводу в плане), т.к. знак легко перепутать при переносе формулы.
- [ ] Сила прикладывается вдоль `dx/r = (x_i - x_j)/r`, то есть от `j` к `i` —
  для `i` это должно быть **отталкивание** (сила увеличивает `dvxdt[i]` в
  направлении от `j`). Проверить знак `+=`/`-=`: `dvxdt[i] += f/m_i`,
  `dvxdt[j] -= f/m_j` — при `f > 0` частицы должны расходиться, не сближаться.
- [ ] Деление на `sys.mass[i]`/`sys.mass[j]` — проверить отсутствие деления на ноль
  (виртуальные частицы или частицы с `mass == 0` уже отфильтрованы `is_contact_pair`,
  но стоит явно подтвердить, что `mass == 0` при `itype > 0` в принципе не встречается
  в данных, иначе — тихий NaN, пойманный только общей проверкой NaN/Inf в конце функции).
- [ ] `contact_type` считывается из `cfg` **один раз до цикла по парам**, не внутри
  цикла (производительность: `switch`/branch не должен повторяться `niac` раз без
  необходимости — хотя корректность от этого не зависит, план явно требовал вынести
  проверку за цикл).
- [ ] `wb.reset_contact()` вызывается **один раз на шаг**, в начале `ext_force`,
  не перед каждой парой и не забыт вовсе (если забыт — `contact_max_delta` и
  `min_dt_contact` будут монотонно расти/сжиматься между шагами, что даст неверную
  диагностику и неверный ограничитель на втором и последующих шагах).

### 4.5 `buffers.hpp` — новые поля

- [ ] `min_dt_contact`, `contact_pair_count`, `contact_max_delta` — инициализированы
  дефолтно (`1e30`, `0`, `0.0`) при создании `WorkBuffers`, не только в `reset_contact()`
  — на первом шаге `reset_contact()` должен быть вызван до первого использования, но
  стоит проверить порядок вызовов в `single_step`/`time_integration`.
- [ ] Комментарий про отсутствие гонок («ext_force обходит пары последовательно») —
  фактически подтвердить, что `ext_force.cpp` не содержит `#pragma omp` над циклом
  по парам (могло появиться при слиянии/рефакторинге).

### 4.6 `time_integration.cpp` — применение ограничителя

- [ ] `if (wb.min_dt_contact < dt) dt = wb.min_dt_contact;` **после**
  `dt = compute_cfl_timestep(...)`, не до (иначе CFL перезапишет контактный лимит).
- [ ] Диагностический вывод обёрнут в `if (cfg.contact_force_type != 0)` — при
  `contact_force_type == 0` вывод и лог **не должны отличаться** от поведения до
  внедрения (это прямая проверка на регрессию для существующих кейсов, не только
  для теста O5 — сверить также реальный текстовый вывод в лог/консоль).

**Это самый рискованный коммит** — численная корректность (знаки, порядок операций,
деление на ноль) здесь важнее стиля.

## 5. `89b233f` — тесты оркестратора (O1–O9)

- [ ] **O1 (баланс импульса)** — проверяется на **сырых** `dvxdt`, без домножения на
  `dt`/интегрирование, т.е. тест эквивалентен `Σ m_k · dvxdt[k] == 0` в пределах 1e-12.
  Убедиться, что тест действительно так и делает, а не проверяет что-то похожее по
  смыслу, но не то же самое.
- [ ] **O5 (`contact_force_type = 0` — бит-в-бит)** — самый важный тест регрессии.
  Проверить, что сравнение идёт **не только** `dvxdt`, но и что тестовый сценарий
  действительно прогоняет пару частиц, которая при `type != 0` дала бы ненулевую силу
  (иначе тест тривиально проходит, потому что контакта и так не было бы).
- [ ] **O9 (регрессия коллапса шага, ×64)** — самый содержательный тест плана.
  Проверить:
  - действительно ли `dt` на каждой итерации пересчитывается через
    `min(dt_cfl_модельный, wb.min_dt_contact)`, воспроизводя логику
    `time_integration.cpp`, а не что-то более простое;
  - критерий "выходит на плато" формализован (например, отношение `dt[63]/dt[32]`
    в некотором диапазоне), а не проверяется визуально/print'ом без ассерта;
  - тест действительно **упал бы**, если бы жёсткость строилась от применяемого
    `dt`, а не от `dt_ref` (т.е. тест значим — стоит мысленно/фактически прогнать
    его на заведомо неверной реализации и убедиться, что он ловит проблему).
- [ ] **O3 (фильтры)** — все три случая (`itype[i]==itype[j]`, `itype[j]<0`,
  `itype[j]==0`) действительно присутствуют как отдельные под-проверки, не слиты
  в одну.
- [ ] Общий вопрос по всем O-тестам: собираются ли реальные объекты `ParticleSystem`
  и `SimulationConfig`, максимально близкие к продовым (через `resize` + `apply_defaults()`),
  или используются урезанные заглушки, из-за которых тест не пройдёт через тот же
  код-путь, что реальный расчёт (например, не забыт ли вызов `apply_defaults()` перед
  выставлением тестовых `contact_force_type`).

## 6. `8ec7558` — документация

Ревью документации — на **фактическое согласие с кодом**, не на стиль:

- [ ] `adr-007-contact-force-types.md` фиксирует принятые решения D1–D6 именно так,

## 7. Сквозные проверки (не привязаны к одному коммиту)

1. **Полная сборка и все тесты.**
   ```
   cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
   cmake --build build -j8
   ctest --test-dir build --output-on-failure
   ```
   Все цели зелёные, включая `contact_test`.

2. **Бит-в-бит регрессия существующих кейсов** (не покрыта юнит-тестами напрямую):
   прогнать штатный кейс (`Initial_Conditions.txt` как есть, `contact_force_type` не
   задан → дефолт 0) до и после диапазона `a4147b9..HEAD` и сравнить выходные `.dat`
   файлы побайтово или с точностью машинного эпсилон. Это единственная проверка,
   которая ловит побочные эффекты рефакторинга `ext_force.cpp` за пределами того,
   что покрыто O5 (O5 сравнивает только `dvxdt` на синтетических данных, не полный
   прогон).

3. **`dim`-независимость.** Код писался и тестировался при `dim = 1`
   ([param.hpp:8](../include/param.hpp#L8) не менялся в этом диапазоне — подтвердить).
   Формально проверить компиляцию (не обязательно физкорректность) при `dim = 2` и
   `dim = 3`: временно поменять константу, пересобрать `test_contact` и `SPH`,
   убедиться, что нет ошибок компиляции в контактном коде (циклы по `dim` в
   `ext_force.cpp` написаны как `for (size_t d = 0; d < dim; ++d)` — должны быть
   корректны при любом `dim`, но это не проверено фактическим прогоном).

4. **Соответствие `Report_SPH_contact.md`.** Явно не требуется — Report описывает
   другую кодовую базу (см. [00-audit.md](00-audit.md)) и не является источником
   истины для этого ревью. Ссылаться на него как на эталон при ревью — ошибка.

5. **Единственный источник истины для чисел.** Любое численное расхождение между
   `part_0.md`, `01-plan.md` и фактическим кодом разрешается в пользу **корректно
   выведенной математики**, проверенной ревьюером самостоятельно (размерность,
   производная, предельные случаи) — не в пользу того, что «так написано в плане»,
   поскольку часть формул в плане (особенно `dt_limit` для вязкой ветки типа 1,
   §3.1 выше) — вывод, сделанный при планировании, а не выверенный внешний источник.

## Формат отчёта ревью

Для каждого найденного дефекта: файл:строка, что не так, конкретный сценарий
(вход → неверный результат), рекомендация «оставить/исправить». Отдельно выделить
дефекты в численных формулах (§3.1, §4.4) — они опаснее стилевых, потому что
дают тихо неверный физический результат, а не сбой сборки.
