# Методы поиска соседних частиц

> Поиск соседей в коде один —
> [`rhs::SpatialIndex<Dim>`](../../../include/rhs/spatial_index.hpp:43). Ключ `nnps`
> читается из `Initial_Conditions.txt` и пишется в чекпоинт, но **ни на что не влияет**.

Поиск соседей строит списки пар взаимодействия — основу парных вычислений SPH
и контактов. Он не привязан к `ParticleSystem`: индекс строится по SoA-массивам
координат, а размерность — параметр шаблона (`Dim`), поэтому один и тот же код
обслуживает Solid (`dim` проекта), нити (`dim = 3`) и расширенное множество
Solid с виртуальными частицами.

## `SpatialIndex<Dim>`

Однородная сетка ячеек с плотным индексированием, построенная сортировкой
подсчётом (count → префиксная сумма → scatter, $O(N)$):

- [`build(coords, n, cell_size)`](../../../include/rhs/spatial_index.hpp:55) —
  размер ячейки `cell_size` задаётся **явно** вызывающим кодом (а не выводится
  из `hsml`). Координаты копируются во внутреннее хранилище; начало сетки —
  минимальная координата, число ячеек по оси — $\lceil \text{range}/\text{cell}\rceil + 1$.
  Рабочая память (счётчики, смещения, буферы потоков) переиспользуется между
  вызовами и только растёт — индекс живёт в рабочей памяти между шагами.
- **Параллельная сборка** — [`build(exec, coords, n, cell_size)`](../../../include/rhs/spatial_index.hpp:115):
  копирование координат, границы (`parallel_reduce` по `min`/`max` с затравкой `coord[0]`, как у
  последовательной версии), ячейка каждой частицы, затем подсчёт частиц по сегментам (число сегментов
  $S=\min(\text{потоки},\,64,\,4N/N_{\rm cell})$), префиксная сумма размеров ячеек и стартовые курсоры
  сегментов; раскладка идёт по возрастанию индекса внутри сегмента. Внутреннее состояние
  (`coord_`, `origin_`, `ncell_`, `eps_box_`, `count_`, `offset_`, `sorted_idx_`) **побитово равно**
  последовательному `build` при любом числе потоков: частицы внутри ячейки остаются в порядке возрастания
  индекса, все величины целые либо точные `min`/`max`. При $S\le1$ используется последовательная
  раскладка.
- **Запас `eps_box_`** $=10^{-9}\,\text{cell}+10^{-12}\,\text{scale}$, где
  $\text{scale}=\max_d(|\text{origin}_d|+n_d\,\text{cell})$ (задаёт `build`). Он нужен обходу
  `for_each_near_cell`: ячейки, чей габарит дальше радиуса $r$ от точки (зазор уменьшается на `eps_box_`,
  порог — $r^2(1+10^{-12})$), и пустые ячейки пропускаются. Порядок оставшихся ячеек прежний, поэтому
  найденные пары совпадают с прежними по составу и порядку; запас гасит округление при отнесении точки к
  ячейке и при вычислении границ. При $2\,\text{reach}+1>16$ обход идёт по всем ячейкам куба.
- «Свой тип» — [`find_pairs`](../../../include/rhs/spatial_index.hpp:242) /
  `find_pairs_parallel`: пары $(i, j)$, $i < j$, $|x_i - x_j| \le r$ и
  `accept(i, j)`; каждая пара выдаётся ровно один раз.
- «Чужой тип» — [`find_pairs_cross`](../../../include/rhs/spatial_index.hpp:258) /
  `find_pairs_cross_parallel`: пары $(a, b)$ между внешним набором точек
  (`other_coords`) и проиндексированным множеством, например нить → Solid.
- Без вектора пар — `for_each_pair_segmented(exec, r, accept, f)`: тот же обход ячеек по отрезкам,
  но `f(seg, i, j)` вызывается сразу при нахождении пары (`seg` — отрезок ячеек). Порядок вызовов
  совпадает с порядком вектора `find_pairs_parallel`; так `build_fiber_contact_search` сразу строит
  primitives, не создавая промежуточный вектор пар.
- Фильтр `accept` — функтор для точной проверки пары (индекс-фильтры,
  попарный радиус); по умолчанию пропускает всё.
- Обход соседних ячеек: [`neighbor_reach(r)`](../../../include/rhs/spatial_index.hpp:429) $=\lfloor r/\text{cell}\rfloor + 1$
  слоёв в каждую сторону, то есть куб $(2\,\text{reach}+1)^{Dim}$ ячеек. При
  `cell_size == r` это 5 ячеек по оси (безопасная, не самая узкая оценка).
- Параллельные варианты (`*_parallel`) используют `CpuExecutor`: диапазон ячеек
  (или внешних точек) режется на фиксированное число отрезков
  `kDetSegments = 64`, каждый отрезок пишет пары в свой буфер, буферы
  склеиваются в порядке отрезков. Порядок пар **не зависит от числа потоков**.

## Потребители

| Взаимодействие | Файл | Тип запроса | Радиус и размер ячейки | Фильтр `accept` |
|---|---|---|---|---|
| Solid-SPH и Solid–Solid-контакт | [`build_solid_sph_search`](../../../include/interactions/solid_sph.hpp:507) | свой тип, по расширенному множеству (реальные + виртуальные) | $r = k\,h_{\max}$, где $k = 2$ при `skf = 1`, иначе $3$; ячейка $= r$ | $i <$ `nreal` и $\lvert x_i - x_j\rvert < k\,(h_i + h_j)/2$ |
| Fiber-Fiber-контакт | [`build_fiber_contact_search`](../../../include/interactions/fiber_contact.hpp) | свой тип, по бусинам | $r = d_{\max} + 2L_{\max}$ (текущая максимальная длина связи) | `object_id[i] != object_id[j]`; в цикле шага дополнительно отсечка `cull_apart` (см. ниже) |
| Fiber-Solid-контакт | [`build_fiber_solid_contact_search`](../../../include/interactions/fiber_solid_contact.hpp) | чужой тип: бусины нитей → Solid-частицы с известным материалом | $r = r_{f,\max} + r_{s,\max}^{contact} + L_{\max}$ | все пары (классификация — при построении примитива) |
| Fiber-Bond | [`compute_fiber_bond`](../../../include/interactions/fiber_bond.hpp:217) | **не** пространственный: обход `topology.bonds` | — | — |

Для Solid индекс даёт широкую фазу с фиксированным радиусом по максимальному
$h$; точный попарный критерий $r < k\,\bar h_{ij}$ проверяется в `accept`,
поэтому поиск корректен для неоднородного `hsml`. Пары «виртуальная–виртуальная»
отбрасываются (`i >= nreal`): вклада в реальные частицы они дать не могут.

### Отсечка далёких пар нить–нить (`cull_apart`)

При `FiberContactBuildOptions::cull_apart = true` (так зовёт цикл шага) в списке primitive остаются
только пары сегментов, не прошедшие консервативный фильтр
[`fiber_contact_surely_apart`](../../../include/interactions/fiber_contact.hpp:642): расстояние между
отрезками не меньше $|\mathbf m_a-\mathbf m_b|-(L_a+L_b)/2$ ($\mathbf m$ — середины, $L$ — длины),
а контакт требует $D<d_{\rm eff}$; радиус $R=d_{\rm eff}+(L_a+L_b)/2$ берётся с запасом
$10^{-8}(d_{\rm eff}+L_a+L_b)+64\,\varepsilon_{\rm mach}\max|x|$ на snapping и округление. Фильтр ложен («не уверен») при некорректном
индексе материала и NaN, тогда решает полная геометрия. Он отбрасывает только пары, которые заведомо
не дали бы контакта, поэтому результат побитово тот же; индексы выживших хранятся вместе с границами
отрезков полного индекса `seg_bound`, чтобы порядок суммирования вкладов не менялся (см.
[Параллелизм](parallelism.md)). Подробнее — [Контакт нитей, §7.7](../models/05-fiber-contact.md#77-ускорение-контакта-нитей-результат-побитово-прежний).
`compute_fiber_contact_diagnostics` в режиме отсечки не поддерживается (исключение). Длина $L_{\max}$
считается один раз за шаг и передаётся обоим поискам (нить–нить и нить–Solid).

## Выход поиска Solid

[`SolidSphSearchResult`](../../../include/interactions/solid_sph.hpp:479)
собирается двухпроходной схемой «счёт → префиксная сумма → запись» по блокам пар
(позиция элемента определяется номером пары, массивы не зависят от числа потоков):

| Массив | Содержание |
|---|---|
| `primitives` | примитивы `SolidSphPrimitive` (`i`, `j`, ядро $w$, $\nabla W$ с $h_{ij}=(h_i+h_j)/2$) для пар (реальная, реальная/виртуальная) |
| `real_pairs` | подмножество пар (реальная, реальная) |
| `contact_pairs` | подмножество `real_pairs` с `body[i] != body[j]` (индекс `k` пары в `real_pairs` идёт в `primitive_id`); по нему работают контактное ядро и диагностика контакта |

Ядро выбирается по `skf` один раз вне цикла: `kernel_cubic` (`1`),
`kernel_gauss` (`2`), `kernel_quintic` (`3`) —
[`kernel.hpp`](../../../include/kernel.hpp).

Если `sph_same_body_only = 1`, пары разных тел не дают SPH-примитива, но остаются
в `real_pairs`/`contact_pairs` (изоляция SPH-сумм по телам; требует
`contact_force_type != 0`, иначе тела не взаимодействовали бы вовсе — исключение
`std::runtime_error`).
