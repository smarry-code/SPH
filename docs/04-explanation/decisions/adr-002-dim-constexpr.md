# ADR-002: Размерность `dim` как compile-time константа

**Статус:** Принято
**Дата:** Подэтап 5.2-В (этап 6.3 «Архитектурная чистота»)

## Контекст

Размерность задачи (1, 2 или 3 оси) определяет размер массивов координат/скоростей
`x[dim]`, `vx[dim]` в [`ParticleSystem`](../../../include/particle_system.hpp:38).
Это структурная характеристика данных: при фиксированной сборке размерность не
меняется в runtime. Изначально многие параметры были неконстантными глобалами в
[`param.hpp`](../../../include/param.hpp), что нарушало ODR и блокировало
безопасное включение заголовков в несколько единиц трансляции.

## Решение

`dim` объявлен как `constexpr size_t`:

```cpp
constexpr size_t dim = 1; // Размерность задачи (1, 2 или 3)
```

Размер C-массивов `x[dim]`/`vx[dim]` определяется на этапе компиляции. Во всех
потребителях пар доступ к координатам/скоростям идёт только через индекс
`d < dim` (циклы `for (d < dim)`) или через константу `0` (ветка `axis_sim`),
поэтому массив размером `dim` корректен при любом `dim` и не расходует память
на неактивные компоненты.

Логические переключатели (`visc`, `axis_sim`, `summation_density`, ...) также
оставлены как `constexpr` — это compile-time ветки компиляции, а не mutable
состояние.

## Последствия

**Положительные:**

- Корректность ODR: `param.hpp` — header-only компиляционный инвариант;
- Отсутствие накладных расходов на размерность в runtime;
- Компилятор оптимизирует циклы по `dim` (размотка, удаление мёртвых веток).

**Отрицательные:**

- Смена размерности требует перекомпиляции;
- Меньшая гибкость по сравнению с runtime-выбором.

## Связанные файлы

- [`param.hpp`](../../../include/param.hpp:16): объявление `dim`.
- [`particle_system.hpp`](../../../include/particle_system.hpp:38): C-массивы `x[dim]`, `vx[dim]`.

## Приписка: значение задаётся при сборке (решение E1)

**Дата:** e2e-тест BC2, [`contact/04-e2e-test-brief.md`](../../../contact/04-e2e-test-brief.md) §2.

Кейс BC2 (осесимметричный удар по карбиду бора) требует `dim = 2`, тогда как
все существующие цели работают при `dim = 1`. Чтобы обе постановки собирались
из одного дерева исходников, значение вынесено в макрос сборки:

```cpp
#ifndef SPH_DIM
#define SPH_DIM 1
#endif
constexpr size_t dim = SPH_DIM;
```

Цель `test_e2e_bc2` компилируется с `target_compile_definitions(... SPH_DIM=2)`,
все прочие цели — без определения макроса, то есть с прежним `dim = 1`.

**Что это НЕ меняет.** `dim` остаётся `constexpr size_t`: размер `x[dim]`/`vx[dim]`
по-прежнему фиксируется на этапе компиляции, runtime-выбора размерности не
появилось, ни одно из положительных/отрицательных последствий выше не
пересматривается. Меняется только то, откуда берётся значение: раньше — литерал
в заголовке (правка файла), теперь — флаг компиляции конкретной цели.

**Ограничение, вытекающее из решения.** Объектные файлы, собранные с разными
`SPH_DIM`, несовместимы по ODR (`ParticleSystem` имеет разный layout). Поэтому
цель с `SPH_DIM=2` обязана компилировать *свои* копии `src/*.cpp`, а не линковаться
с объектниками цели `SPH`. В CMake это выражено тем, что `test_e2e_bc2` получает
полный список исходников конвейера в своей команде `add_executable`.

## Актуальное состояние (2026-11)

- Значение `dim` берётся из макроса `SPH_DIM` ([`param.hpp:16`](../../../include/param.hpp:16)).
  Основной исполняемый файл `SPH` получает его из кеш-переменной CMake `SPH_DIM`
  (1, 2 или 3; по умолчанию 1, [`CMakeLists.txt:46`](../../../CMakeLists.txt:46);
  `target_compile_definitions(SPH PRIVATE SPH_DIM=...)`).
- Тестовых целей с собственным `SPH_DIM` стало несколько (`test_axisym` — 2,
  `test_kinematics_3d`, `test_fiber_model` — 3 и др.); все они, как и `test_e2e_bc2`,
  компилируют собственные копии исходников конвейера (`SPH_PIPELINE_SOURCES`).
- Нити и режим `solid_fiber` требуют `SPH_DIM=3`; при иной размерности разбор ключей
  `fiber_file` и `k_mode=solid_fiber` завершается ошибкой.
