# ADR-011: Раздельные постановки кейсов для регрессии и экспериментов

**Статус:** Принято
**Дата:** 2026-11-20

## Контекст

Постановки опытов (BC2, BC6, уменьшенный BC2 в 3D, Guo 2019) лежали в `tests/` и служили двум
ролям сразу:

- **регрессия:** снимки `test_regression`, e2e smoke, `test_energy_log`, `test_fiber_plasticity_guo` и
  другие цели `ctest`. Им нужна постановка, которая не меняется: иначе снимки и допуски перестают
  что-либо значить;
- **эксперименты:** утилита серийных выстрелов `guo2019_shot`, `fabric_checks`, `fiber_t0_dump`,
  полные прогоны `test_e2e_bc6 --full` из журналов `experiments/`. Им нужна постановка, которую можно
  менять под расчёт: новые ключи, мониторы, раскладки ткани.

Общая копия заставляла выбирать между двумя плохими вариантами: каждая правка под эксперимент
рисковала побитовой регрессией, а заморозка регрессии мешала расчётам. Исходные данные опытов и
код постановок к тому же лежали в разных местах (`Керамика/`, `tests/`, `tests/data/`, `tools/`).

## Решение

Код, числа и данные постановки каждого опыта живут в `cases/<кейс>/` и разделены по ролям
([правила](../../../cases/README.md#роли-постановок)):

- `cases/<кейс>/source/` — архив исходных данных опыта, не правится;
- `cases/<кейс>/regression/` — **замороженная** постановка, которую берёт только `ctest`: код сцены,
  числа опыта, `initial_conditions.txt`, `reference.txt`, снимки регрессии `snapshots/`;
- `cases/<кейс>/experiment/` — **живая** копия постановки и драйверы расчётов. Заводится, когда кейс
  нужен для расчётов; сейчас есть только у Guo 2019;
- `cases/common/` — общая библиотека, не зависящая от кейса: обвязка (`e2e_harness.hpp`), энергии и
  импульсы (`energy.hpp`), правило числа ячеек решётки (`lattice.hpp`). Её берут обе стороны.

Копии одного кейса называются одинаково: те же имена файлов и пространства имён. Нужную копию цели
выбирает CMake: `sph_case(<цель> <кейс> regression|experiment)`. Дублирование кода между копиями
допускается сознательно.

`regression/` меняется только при подстройке под изменённый API ядра без изменения поведения
(регрессия проходит побитово) или по решению владельца с перегенерацией эталонов. Проверки самих
экспериментальных утилит (`checkpoint_cli_test`, `stitch_kt_cli_test`, `mosaic_kt_cli_test`,
`fabric_checks_smoke_*`) собираются из `experiment/`: они проверяют утилиту, а не физику постановки.

## Альтернативы

- **Одна копия в `tests/`** (как было): нет дублирования, но регрессия и эксперименты мешают друг другу.
- **Копии вспомогательного кода** в каждой стороне: полная независимость, но правки обвязки пришлось
  бы вносить дважды. Обвязка от кейса не зависит, поэтому выбрана одна общая библиотека.

## Последствия

**Положительные:**
- правка постановки под расчёт не трогает регрессию; расхождение копий видно через
  `diff -r cases/<кейс>/regression cases/<кейс>/experiment`;
- всё об опыте — исходные данные, постановка, эталоны, карточка со ссылками на эксперименты — в одном
  каталоге.

**Отрицательные:**
- две копии постановки Guo 2019 (около 3,4 тыс. строк). Исправление, нужное обеим, вносится дважды:
  в `experiment/` свободно, в `regression/` — по правилам заморозки;
- правка `cases/common/` затрагивает обе стороны и проверяется полным `ctest`.
