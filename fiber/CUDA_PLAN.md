# План: CUDA-версия конвейера Solid + Fiber

Документ описывает, как перенести на GPU (CUDA) конвейер, реализованный по [SPH.md](SPH.md) и описанный в [IMPLEMENTATION_REPORT.md](IMPLEMENTATION_REPORT.md): поиск соседей → primitives → interaction kernels → contributions → reduce → finalize → ODESolver → Postprocessing. Здесь: какие решения принимаются, что из CPU-кода переиспользуется, в каком порядке идут этапы и чем проверяется каждый из них.

Уравнения взаимодействий и динамики не меняются — они в SPH.md. CUDA-версия считает ту же физику, что и CPU-версия; эталоном для каждого этапа служит CPU-путь.

**Ветка:** `fiber_cuda`, worktree `C:/dip/sph/SPH-cuda`.
**База:** ветка ответвлена от коммита `3b9873c` (ветка `fiber_new`, Ф0–Ф8 завершены); этап ГF — коммиты `31c469d`, `e77b21a`. Работа из `fiber_new` после ответвления (вывод кадров нитей из `time_integration`, демо «снаряд и сеть из нитей» в `experiments/2026-09-26-fiber-net-demo/`, подробный раздел тестов в IMPLEMENTATION_REPORT.md) влита коммитом `fd58a4c`; быстрый набор после слияния — 62/62.

**Изменения плана:**

Этап выполнен, результаты — в [FP32_REPORT.md](FP32_REPORT.md) и в §4 (ГF). Решение Р-Г6 о точности пересмотрено.

### 1.2. Что уже есть в CPU-коде и помогает переносу

Архитектура Ф1–Ф8 изначально проектировалась с расчётом на GPU (SPH.md, последний абзац: «…позволяет использовать те же математические interaction kernels при последующей реализации другого backend, в частности GPU»). Конкретно:

- **SoA-хранение** Solid (`ParticleSystem`) и Fiber (`FiberState`) — прямо ложится на coalesced-доступ GPU.
- **Нет атомарных операций и раскраски графа.** Kernels пишут вклады, суммирование — отдельной стадией reduce по владельцу. На GPU это переносится без изменения смысла (§3.4).
- **Primitives хранят индексы, а не указатели**; разные типы primitives — разные массивы, без полиморфизма.
- **Состояние на время RHS только читается**; всё изменяемое — во временных буферах одного RHS.
- **Двухпроходная схема count → prefix sum → fill** уже заложена в SPH.md для поиска и reduce — это стандартный GPU-приём.
- **Детерминированный режим reduce** (канонический порядок `interaction_type, primitive_id, slot`) — на GPU он получается бесплатно при выбранной схеме reduce (§3.4) и даёт точку побитного сравнения с CPU.
- **Переключаемая точность (ГF).** Вся арифметика конвейера — над `real_t`, литералы записаны как `real_t(...)`, в fp32-сборке нет ни одного неявного повышения до `double`. Для GPU это значит, что общие функции (§3.2) сразу пишутся под обе точности, а у fp32 уже есть CPU-эталоны (`tests/data/regression_fp32/`).

## 2. Принятые решения

Решения обозначены **Р-Г1…Р-Г10**, этапы (§4) — **ГF, Г0…Г12**.

| № | Решение | Следствие |
|---|---|---|
| Р-Г1 | **Компилятор — связка `nvcc` + Clang (решение владельца, 2026-09-27).** `.cu`-файлы компилирует `nvcc` 13.4, весь остальной проект (`.cpp`, тесты, конвейер CPU) — Clang 22, как сейчас; всё в одной CMake-сборке (`CXX=clang++`, `CUDA=nvcc`), связка проверена (§1.1). Хост-часть `.cu` на Windows `nvcc` компилирует только через MSVC `cl` 19.51 (`-ccbin clang` на Windows не поддерживается); на Linux — через Clang (`CMAKE_CUDA_HOST_COMPILER=clang++`), если установленная версия `nvcc` поддерживает эту версию Clang, иначе через GCC. Clang как компилятор CUDA не используется | (1) Заголовки, которые включаются в `.cu` (`precision.hpp`, `include/physics/*`, представления, `DeviceBuffer`), обязаны компилироваться **и Clang, и `cl`**: без clang-специфичных расширений, `#pragma clang` — только под `#ifdef __clang__`. (2) Сборка CUDA-целей на Windows идёт из окружения `vcvars64.bat` — Г0 даёт для этого скрипт и CMake-пресет. (3) `-Weverything` не покрывает `.cu`; для `nvcc` включаются свои предупреждения (`-Xcompiler=/W4` на хосте). Делать ли их ошибками, решается в Г0 по объёму шума от заголовков CCCL. (4) Объекты `cl` и Clang линкуются вместе (оба — MSVC ABI и одна STL), проверено спайком. Решение фиксируется в ADR-009 |
| Р-Г1а | **Две машины: Windows + RTX 4050 (разработка) и Linux + карта NVIDIA неизвестной модели (ответ владельца).** Архитектуры — кэш-переменная `SPH_CUDA_ARCHITECTURES`. По умолчанию `89-real;75-virtual`: машинный код для RTX 4050 и PTX **младшей** поддерживаемой архитектуры — PTX архитектуры X запускается только на картах не ниже X, поэтому PTX `75` подходит любой карте начиная с Turing, а PTX `89` не подошёл бы, например, A100 (`sm_80`). На Linux-машине сборка конфигурируется с `SPH_CUDA_ARCHITECTURES=native` (CMake ≥ 3.24 сам определяет установленную карту). Минимальная версия CUDA — **12.4**, а не 13: CUDA 13 не поддерживает карты старше Turing (`sm_75`), и если на Linux-машине, например, V100 или карта серии Pascal, там понадобится CUDA 12.x | Код не использует возможностей, которых нет в CUDA 12.4 и на `sm_75`/`sm_70`, и не завязывается на 6 ГБ (лимиты — из `cudaGetDeviceProperties`) и на Windows (флаги `/Zc:*` — только при MSVC-хосте, пути — через `CUDAToolkit`). Сборку на CUDA 12.x проверяем на машине разработки: CUDA 12.6 установлена рядом. Linux-сборка и `test_cuda_toolchain` прогоняются на второй машине, как только будет доступ (Г0, затем в конце Г5, Г9, Г11) |
| Р-Г2 | **Одна математика на оба backend.** Физика одного primitive/частицы — inline-функции с макросом `SPH_HD` (`__host__ __device__` под CUDA, пусто иначе). CPU-kernels переводятся на них **до** написания GPU-кода, под побитной регрессией | Ошибка в формуле не может «разойтись» между CPU и GPU; GPU-этапы проверяют только инфраструктуру и порядок операций |
| Р-Г3 | **CPU-путь остаётся эталоном и основной сборкой.** CUDA включается опцией CMake `SPH_ENABLE_CUDA` (по умолчанию `OFF`) и ключом конфигурации `backend = cpu \| cuda` (по умолчанию `cpu`) | При `OFF` сборка, флаги и 62 теста (44 fp64 + 18 fp32) не меняются. Регрессионные эталоны fp64 и fp32 не перегенерируются |
| Р-Г4 | **Состояние живёт на GPU весь расчёт.** Копирование на хост — только для вывода кадров, строки монитора в `log.txt`, редких событий разрыва нитей и диагностики при ошибке | Цель — не больше 1–2 синхронизаций хоста на шаг (§3.9) |
| Р-Г5 | **Reduce — по SPH.md, без атомарных операций:** каждый primitive пишет вклады в свои фиксированные слоты, затем вклады группируются по частице-получателю сортировкой и суммируются владельцем в каноническом порядке | Результат GPU детерминирован от запуска к запуску; в канонический порядок входят `interaction_type, primitive_id, slot` — ровно как в SPH.md. Атомарные сложения в физике не используются |
| Р-Г6 | **Точность — `real_t` из [`include/precision.hpp`](../include/precision.hpp)** (этап ГF): весь GPU-код пишется над `real_t` и собирается и в fp64, и в fp32 тем же макросом `SPH_PRECISION`; у каждой GPU-цели есть пара `*_cuda` и `*_cuda_fp32`. Эталоном корректности GPU остаётся fp64 (сверка с CPU fp64). fp32 на GPU проверяется против CPU fp32 и его эталонов (`tests/data/regression_fp32/`). **Основной режим GPU — fp32 (решение владельца, 2026-09-27).** fp64-сборка GPU сохраняется как эталон корректности и как режим для кейсов, где fp32 недостаточно точен ([FP32_REPORT.md](FP32_REPORT.md): на полном BC2 fp32 даёт −1 % пика, но заметно расходится на пороговой физике — контакт типов 2–3, JH-2) | Оптимизация (Г11) и замеры скорости ведутся для fp32; fp64 на GPU должен быть корректным, но не обязан быть быстрым. Ошибки переноса ловятся сверкой GPU fp64 с CPU fp64, поведение рабочего режима — сверкой GPU fp32 с CPU fp32 и с эталонами fp32 |
| Р-Г7 | **Порядок этапов: 3D Solid → нити → 2D осесимметричный Solid.** Нити существуют только в 3D (Р9); для 3D Solid уже есть эталон `regression_bc2mini3d_*`. 2D с зеркальными частицами (BC2/BC6) — после нитей | Первый сквозной результат на GPU — 3D Solid без нитей, затем нити по одной физике за этап |
| Р-Г8 | **Ограничения CPU-версии переносятся как есть:** радиус поиска нитей по `l0`, `sle = 2` не поддерживается, нет трения, нет самоконтакта нити | GPU не должен давать отличий в поведении, только в скорости |
| Р-Г9 | **Индексы на GPU — `uint32_t`**, на CPU остаётся `rhs::index_t = size_t`. Общие `SPH_HD`-функции принимают индексы шаблонным параметром или получают уже прочитанные значения | Экономия памяти и полосы; предел — 4·10⁹ частиц, заведомо больше 6 ГБ |
| Р-Г10 | **Процесс — как в Ф0–Ф8:** каждый этап — код, независимое ревью (перечитать SPH.md и этот план, проверить формулы и граничные случаи), сборка, полный прогон тестов координатором | Каждый этап — отдельный коммит (+ коммит правок ревью) |

## 3. Архитектура CUDA backend

### 3.1. Соответствие CPU → GPU

| CPU (как сейчас) | GPU (что будет) | Примечание |
|---|---|---|
| `rhs::CpuExecutor` (`parallel_for/reduce/scan/sort`) | `rhs::CudaExecutor`: `parallel_for(n, device_lambda)` + обёртки над `cub::DeviceReduce/Scan/RadixSort/Select`, поток (`cudaStream_t`) и временная память CUB из workspace | Интерфейс по смыслу тот же; physics-код не видит `<<<>>>` |
| `ParticleSystem` | `DeviceSolidState` — SoA из `DeviceBuffer<real_t>`/`<int>` | Только поля, нужные RHS/решателю/прочности |
| `FiberState`, `FiberTopology` | `DeviceFiberState`, `DeviceFiberTopology` (`prev`, `next`, массивы полей `FiberBond`) | Топология меняется только при разрыве (§3.8) |
| `Materials`, `std::vector<FiberMaterial>` | `MaterialTable` (POD из `real_t`, передаётся в ядра по значению или через `__constant__`), `FiberMaterialTable` | Размер < 4 КБ |
| `SolidDerived` (p, c), `SolidExtended`, `GhostSet` | буферы в `CudaRhsWorkspace` | Ghost — только при `dim = 2` (Г10) |
| `SpatialIndex<Dim>` | `DeviceSpatialIndex<Dim>` на отсортированных ключах ячеек (§3.3) | Одна структура на тип частиц, общая для нескольких interaction types |
| `find_pairs_parallel` → `std::vector<pair>` → цикл построения primitives | одно ядро «поиск + построение primitive» по схеме count → scan → fill | `W`, `∇W` считаются при заполнении, как сейчас |
| `ContributionBuffer` по потокам + `reduce_contributions` по шардам | `ContributionPool<Delta>` со слотами + CSR «частица → список слотов» + ядро суммирования (§3.4) | Owner computes: одна частица — один поток |
| `finalize_solid` (`parallel_for` по частицам) | ядро по частицам, та же `SPH_HD`-функция | |
| `PredictorCorrectorSolver`, `EulerSolver` | `ode::cuda::PredictorCorrectorSolver`, `ode::cuda::EulerSolver` — ядра по частицам над теми же формулами | Буферы `f^{n-1}` и `y^n` — на GPU |
| `compute_cfl_timestep`, `dt_limit` всех типов | редукции `min` на GPU; итоговый `dt` — скаляр в памяти GPU | Хост получает `dt` асинхронно (§3.9) |
| `apply_material_strength`, `update_smoothing_length` | ядра по частицам | Мизес, JH-2 (после Г2 — без шима), `sle = 1` |
| `find_fiber_break_events` / `apply_fiber_break_events` | поиск событий на GPU; применение — существующий CPU-код на хосте, только при наличии событий | Разрыв — редкое событие, последовательное применение сохраняет детерминизм |
| `time_integration(...)` | `time_integration_cuda(...)`: тот же порядок шагов цикла | Выбор по `cfg.backend` в `main.cpp` |

### 3.2. Общая математика (`SPH_HD`)

Новый каталог `include/physics/` с чистыми inline-функциями без выделения памяти, исключений и STL-контейнеров:

```text
include/physics/hd.hpp               SPH_HD, sph_min/sph_max, коды ошибок
include/physics/material_table.hpp   MaterialTable, ElasticTable, FiberMaterialTable (POD) + сборка из Materials
include/physics/sph_kernel.hpp       W, ∇W для skf = 1/2/3
include/physics/eos.hpp              p_gas, p_art_water, Ми-Грюнайзен, Тэт, JH-2 + диспетчер по itype
include/physics/solid_sph_pair.hpp   вклад одного SolidSphPrimitive: di, dj
include/physics/solid_finalize.hpp   finalize одной частицы (осевые члены, Гук + Яуманн, энергия)
include/physics/solid_contact_pair.hpp  геометрия + penalty_force (contact_force.hpp получает SPH_HD)
include/physics/fiber_bond_pair.hpp
include/physics/fiber_contact_geom.hpp  4 геометрических случая, веса Meyer
include/physics/fiber_solid_geom.hpp
include/physics/strength.hpp         Мизес, JH-2 с явными аргументами
include/physics/ode_update.hpp       формулы предиктора/корректора/Эйлера для одной частицы
```

Все эти функции работают над `real_t` (ГF уже перевёл на него типы и литералы конвейера, см. правило литералов в `precision.hpp`), поэтому одна и та же функция собирается в fp64 и fp32 на хосте и на устройстве.

Доступ к состоянию — через «представления» с сырыми указателями, одинаковые для хоста и устройства:

```text
SolidView      { const real_t* x[dim]; const real_t* vx[dim]; const real_t* mass; ... ; uint32 n; }
FiberView      { const real_t* x[dim]; ...; const int* object_id; const int* material_id; }
TopologyView   { const long long* prev; const long long* next; ... }
```

CPU строит представление над `std::vector::data()`, GPU — над `DeviceBuffer`. Kernel на CPU остаётся лямбдой в `exec.parallel_for`, но внутри — вызов общей функции; `ContributionWriter` остаётся CPU-деталью.

**Требование к Г2:** порядок арифметических операций при выносе в функции не меняется, поэтому CPU-путь обязан остаться **побитно** тем же в обеих точностях: однопоточные снимки fp64 и fp32 совпадают байт в байт с эталонами (так же, как это проверялось в ГF), BC2 full — тот же пик 985.0 м/с при 1.312 мкс. На хосте `SPH_HD`-функции вызывают те же `std::pow/std::sqrt`, что и сейчас.

Под Windows `windows.h` определяет макросы `min`/`max`, которые ломают CUB (§1.1): CUDA-цели компилируются с `NOMINMAX`, а `SPH_HD`-заголовки используют `sph_min`/`sph_max` из `physics/hd.hpp`.

### 3.3. Поиск соседей на GPU

`DeviceSpatialIndex<Dim>`:

1. Редукция bounding box (min/max по осям) — на GPU.
2. Ключ ячейки каждой частицы: 64-битный линейный индекс `floor((x - origin)/cell)`.
3. `cub::DeviceRadixSort::SortPairs(key, particle_index)` — стабильная сортировка.
4. `cub::DeviceRunLengthEncode` → массив уникальных ячеек `(cell_key, start, count)`.
5. Запрос соседей частицы: перебор `(2·reach+1)^Dim` соседних ячеек, поиск каждой в массиве уникальных ключей бинарным поиском; `reach = floor(radius/cell) + 1` — та же безопасная оценка, что в CPU-версии (дефект §5 отчёта не повторяется).

Почему не плотная сетка, как на CPU: число ячеек плотной сетки растёт с объёмом bounding box, а в сценах с разлетом осколков или снарядом (демо «сеть из нитей») это кубически раздувает память. Сортированные ключи занимают O(N) при любом разбросе частиц.

Поиск и построение primitive — одно ядро в два прохода (SPH.md, «count → prefix sum → fill»):

- **count:** поток на частицу `i` считает допустимых соседей (`j > i` для одного типа; фильтр `accept` конкретного interaction type);
- **scan:** `cub::DeviceScan::ExclusiveSum` → смещения; итог копируется на хост для размера буфера (§3.9);
- **fill:** тот же обход, запись primitive в свою позицию. Порядок primitives — по `i`, внутри — по порядку обхода ячеек, то есть детерминирован.

Фильтры по типам взаимодействий (как в CPU):

| Interaction type | Индекс | Фильтр `accept` |
|---|---|---|
| Solid-SPH | Solid (+ ghost при dim=2) | `i < nreal`, `r < scale_k·(h_i+h_j)/2` |
| Solid-Solid-Contact | те же пары Solid-SPH, подмножество `(real, real)` | `body[i] != body[j]` проверяется в kernel, как сейчас |
| Fiber-Fiber-Contact | Fiber | `object_id[i] != object_id[j]` |
| Fiber-Solid-Contact | запрос бусин Fiber к индексу **Solid** | `j < nreal`, `itype[j]` допустим по `ElasticTable` |
| Fiber-Bond | без поиска — массив связей | — |

Отличие от CPU: Fiber-Solid-Contact ищет по уже построенному индексу Solid (SPH.md прямо это допускает: «одна и та же построенная spatial structure может использоваться несколькими interaction types»), а не строит отдельный индекс по подмножеству допустимых частиц. Множество найденных пар то же, порядок другой — сравнение с CPU ведётся с точностью до порядка (§5).

### 3.4. Contributions и reduce без атомарных операций

У каждого типа primitive — фиксированное число слотов вклада:

| Primitive | Слоты в пул Solid | Слоты в пул Fiber |
|---|---|---|
| `SolidSphPrimitive` | 2 (`i`; `j` — пустой, если `j` ghost) | — |
| `SolidContactPrimitive` | 2 (пустые, если контакта нет) | — |
| `FiberBondPrimitive` | — | 2 |
| `FiberContactPrimitive` | — | до 4 (`i`, сосед `i`, `j`, сосед `j`; отсутствующие — пустые) |
| `FiberSolidContactPrimitive` | 1 (`s`) | 2 (`a`, `b`; `b` пустой в точечном контакте) |

Схема:

1. Kernel пишет `Delta` в слот `base_type + slot_count·k + slot` и цель (`target` или `kNone`) — без гонок, адрес вклада однозначен.
2. Пулы одного типа частиц (Solid: Solid-SPH | Solid-Contact | Fiber-Solid; Fiber: Bond | Fiber-Fiber | Fiber-Solid) — непрерывные отрезки одного массива в порядке `interaction_type`.
3. `cub::DeviceRadixSort::SortPairs(target, slot_index)` (стабильно, пустые слоты с ключом `kNone` уходят в конец) → CSR `offsets[particle]`.
4. Ядро reduce: поток на частицу суммирует свои вклады в порядке `slot_index`. Этот порядок и есть канонический `(interaction_type, primitive_id, slot)` из SPH.md.

Следствия:

- результат детерминирован независимо от расписания GPU;
- при совпадающих номерах primitives и одинаковых вкладах сумма **побитно** совпадает с CPU `reduce_contributions` в детерминированном режиме — на этом строится тест инфраструктуры в Г3;
- вклад Fiber-Solid-Contact в Solid идёт через тот же reduce, что Solid-SPH и Solid-Contact (сейчас на CPU он прибавляется к `dvx` отдельным циклом после `single_step`). Для физики это то же самое, но порядок сложения другой — учитывается в допусках сравнения.

Оптимизация (Г11, по результатам профилирования): для Solid-SPH — режим «owner pull», когда поток частицы `i` сам обходит всех соседей и считает свою половину вклада пары. Вклады не хранятся (экономия ~10 КБ на частицу, §3.6), но парная функция считается дважды. Он тоже детерминирован и без атомарных операций; включается параметром `cuda_reduce_mode = pool | pull`.

### 3.5. Граф одного RHS на GPU

Повторяет граф из SPH.md, ветви Solid и Fiber — в разных потоках CUDA с синхронизацией событиями:

```text
stream S:  EOS → [ghost, dim=2] → SolidIndex → Solid-SPH search+prim → Solid-SPH compute ─┐
                                              └→ Solid-Contact compute (+dt, диагностика) ─┤
stream F:  FiberIndex → Fiber-Fiber search+prim → compute (+dt) ─────────────────────────┐ │
           Fiber-Bond compute (+dt) ─────────────────────────────────────────────────────┤ │
           (ждёт SolidIndex) Fiber-Solid search+prim → compute (+dt) ────────────────────┼─┤
                                                                                         ▼ ▼
                                                                         Fiber reduce  Solid reduce → finalize
```

`Fiber reduce` ждёт все три fiber-ветви, `Solid reduce` — Solid-SPH, Solid-Contact и Fiber-Solid. На первом проходе (Г4–Г8) допустимо всё в одном потоке; разнесение по потокам — в Г11, когда будет что перекрывать.

### 3.6. Память

Оценка для 3D, кубический сплайн (`skf = 1`, радиус 2h, h ≈ 1.3·Δx): ~74 соседа, ~37 пар `i<j` на частицу.

| Буфер | На частицу | Комментарий |
|---|---|---|
| Состояние Solid + буферы решателя (`f^{n-1}`, `y^n`) | ~0.5 КБ | ~60 `double` |
| `SolidSphPrimitive` (2×`uint32` + W + ∇W) | ~1.5 КБ | 40 Б × 37 |
| Пул `SolidDelta` (18 `double` в 3D) | ~10.7 КБ | 144 Б × 74 слота |
| Сортировка/CSR/временная память CUB | ~1 КБ | |
| **Итого** | **~14 КБ** | потолок ~350 тыс. частиц Solid на 6 ГБ |
| **Итого в fp32** | **~7.5 КБ** | потолок ~650 тыс. частиц (индексы и служебные массивы не уменьшаются) |

Режим `pull` (Г11) убирает пул вкладов и поднимает потолок до ~2 млн частиц. Буферы растут и не освобождаются между RHS (как `RhsWorkspace`); при нехватке памяти — понятное исключение с оценкой требуемого объёма, а не падение внутри CUB.

### 3.7. Ошибки и диагностика на GPU

- Проверки, которые на CPU бросают исключение (ρ ≤ 0 или NaN, `mass` ≤ 0, неизвестный `itype`, r = 0 у оси, NaN/Inf в `h`, `Diagnostics::validate`), на GPU пишут код ошибки частицы; редукция `max` по кодам даёт один флаг на шаг.
- Флаг читается хостом вместе с `dt` (без дополнительной синхронизации). При ошибке хост скачивает состояние и вызывает существующую CPU-проверку — она печатает то же сообщение и бросает то же исключение, что и CPU-путь.
- Макрос `SPH_CUDA_CHECK` на каждом вызове CUDA API; после каждого ядра в отладочной сборке — `cudaGetLastError` + синхронизация.
- NVTX-диапазоны на всех стадиях — для Nsight Systems.

### 3.8. Цикл по времени на GPU

`time_integration_cuda` повторяет `detail::run_time_integration` **в том же порядке**, включая неочевидное место пересчёта h:

1. `solver.predict` (нет на первом шаге PredictorCorrector и у Эйлера).
2. RHS Solid (EOS, поиск, Solid-SPH, Solid-Contact, reduce, finalize, диагностика контакта).
3. `update_smoothing_length` (sle = 1) — **сразу после RHS Solid, до CFL**: на предсказанной ρ, как требует шапка `postprocessing.hpp`.
4. RHS Fiber: Bond, Fiber-Fiber, Fiber-Solid (+ вклад в Solid).
5. `dt = min(CFL, dt_contact, dt_bond, dt_fiber_contact, dt_fiber_solid)` — на GPU.
6. `solver.advance`.
7. Postprocessing: Мизес/JH-2 (читают `drho` и скорости деформаций этого RHS), поиск разрывов нитей → при наличии событий: скачать топологию, `apply_fiber_break_events` на хосте, закачать обратно.
8. Вывод кадра при `time ≥ next_output_time` (скачивание состояния), строка монитора в `log.txt`, `RunGuard`.

`dt` из шага n нужен как `dt_applied` контакта типа 3 на шаге n+1 — он и так лежит на GPU.

### 3.9. Синхронизация хоста

Неизбежные точки на шаг в первой версии:

- размеры списков пар после scan (по одной на тип поиска) — для выделения памяти;
- `dt` + флаг ошибок + счётчик событий разрыва — одно чтение в конце шага;
- `vx` частицы-монитора — асинхронное копирование одного `double` в pinned-буфер, запись в файл пачками.

Оптимизация (Г11): буферы пар с запасом и флагом переполнения (повтор шага при переполнении, что редко) → один `cudaStreamSynchronize` на шаг; затем захват шага в CUDA Graph, что особенно полезно под WDDM.

### ГF. Версия расчёта в fp32 — выполнено

Вставлен первым по решению владельца (см. начало документа). Подробности и все числа — в [FP32_REPORT.md](FP32_REPORT.md).

- `include/precision.hpp`: `real_t = double | float` по макросу `SPH_PRECISION` (64 по умолчанию). Переменные состояния, производные, primitives, материалы и арифметика kernels — `real_t`. Часы расчёта (`time`, `dt`, `t_total`), параметры конфига и ввод/вывод остаются `double`.
- Вещественные литералы в арифметике — `real_t(2.0)`. fp32-цели собираются с `-Wdouble-promotion -Wimplicit-float-conversion`; в файлах конвейера предупреждений ноль.
- fp64 не изменился **побитно**: 24 однопоточных снимка регрессии до и после совпадают байт в байт, 44/44 теста.
- Регрессия fp32: `test_regression_fp32`, `test_regression_3d_fp32` (14 тестов, метка `fp32`), эталоны `tests/data/regression_fp32/`, допуски откалиброваны по той же методике, что у fp64; цель `regression_golden_fp32`.
- Сквозной BC2 в fp32: `test_e2e_bc2_fp32`.
- Итоги: fp32 на CPU быстрее fp64 на 8–17 % на кейсах регрессии и на ~17 % на полном BC2 (≈ 363 с против 440 с). Полный BC2 в fp32: пик монитора 975.0 м/с против 985.0 м/с у fp64 (−1 %), фронт совпадает до 3.5 нс. Пороговая физика (`e_pl`, `D`, контакт типов 2–3) в fp32 расходится с fp64 заметно; на BC6 с контактом типа 3 fp32 включает контакт уже на первом шаге (начальная сборка точно на касании).
- Быстрый набор тестов: 62/62 (44 прежних + 18 fp32).

- `include/physics/*` по §3.2; `MaterialTable`, `ElasticTable`, представления `SolidView/FiberView/TopologyView`. - CPU-kernels всех пяти interaction types, `compute_solid_derived`, `finalize_solid`, решатели, прочность и `update_smoothing_length` переводятся на общие функции.
- JH-2 на явных параметрах: `prochnost_cem_JH2` получает скорости деформаций/поворота аргументами; шим записи `sys.exx..ryz` в `single_step` удаляется **в том же коммите** (как требует комментарий у `SolidFinal`).
- Всё, что попадает в `SPH_HD`, собирается пробной `.cu`-целью (без запуска) — компилируемость под CUDA проверяется сразу.

**Готово, когда:** однопоточные снимки fp64 и fp32 **побитно** совпадают с эталонами (без перегенерации); 62 + новые тесты Г1 зелёные; `test_e2e_bc2 --full` — пик 985.0 м/с при 1.312 мкс, `test_e2e_bc2_fp32 --full` — 975.0 м/с при 1.3284 мкс.

**Риск:** самый рискованный CPU-этап — трогает всю физику. Смягчение: по одному interaction type за коммит, регрессия после каждого.

### Г3. GPU-инфраструктура без физики

- `DeviceBuffer<T>` (RAII, рост без освобождения), `PinnedBuffer<T>`, `CudaContext` (выбор устройства, потоки, события), `CudaExecutor`, `CudaRhsWorkspace`, `SPH_CUDA_CHECK`, NVTX.
- `DeviceSpatialIndex<Dim>` (§3.3): same-type и cross-запросы с `accept`, count → scan → fill.
- `ContributionPool<Delta>` + CSR-reduce (§3.4).
- Тесты (аналоги `executor_test`, `spatial_index_test`, `contributions_test`):
  - множество пар GPU = полному перебору, в 2D и 3D, N ∈ {0, 1, 2, 50, 400, 10⁵}, `cell < radius`, `cell > radius`, пустые наборы, фильтр `accept`, разброс частиц на 10⁶ ячеек (проверка отсутствия плотной сетки);
  - reduce GPU **побитно** = CPU `reduce_contributions(deterministic)` на одинаковых primitives;
  - повторный запуск даёт побитно тот же результат.

Инфраструктура шаблонна по типу данных, поэтому тесты гоняются и для `real_t = double`, и для `float`.

**Готово, когда:** все тесты `cuda` этапа зелёные в обеих точностях; `compute-sanitizer --tool memcheck` и `racecheck` без ошибок.

### Г4. Состояние на GPU и Solid RHS (3D)

- `DeviceSolidState`, `DeviceFiberState`, `DeviceFiberTopology`, `upload/download`; тест «туда-обратно» — побитно.
- Ядра: EOS → поиск + `SolidSphPrimitive` (W, ∇W) → Solid-SPH → Solid-Contact (+ `dt_limit`, число пар, max проникание) → reduce → finalize, коды ошибок.
- Тест `cuda_rhs_equivalence_3d`: на состоянии `bc2mini3d` после 0 и после K CPU-шагов, для `contact_force_type` 0–3 — одно вычисление RHS на CPU и на GPU:
  - множество пар Solid-SPH и Solid-Contact совпадает;
  - `drho, du, dv, ds*, exx..ryz, xsph` — относительное расхождение ≤ 1e-12 (сборка с `-fmad=false` — ≤ 1e-14);
  - `min_dt_contact`, `contact_pair_count` — совпадают;
  - то же для fp32 (`cuda_rhs_equivalence_3d_fp32`, GPU fp32 против CPU fp32) с допуском ≤ 1e-5 отн.; если контакт стоит точно на пороге и число контактных пар расходится, такие пары разбираются поимённо, а не прячутся в допуск.

**Готово, когда:** эквивалентность RHS на всех четырёх типах контакта, memcheck чистый.

### Г5. Решатель и цикл по времени на GPU для Solid (3D)

Если на N = K допуск CPU не выдерживается из-за другого порядка суммирования (контакт и JH-2 — пороговые, расхождения на уровне округления растут), вводятся отдельные GPU-допуски с письменным обоснованием; эталоны не меняются;

### Г11. Производительность

Только после того, как корректность подтверждена Г4–Г10.

- Оптимизируется рабочий режим fp32 (Р-Г6). Бенчмарк `bench_cuda` на RTX 4050 и на Linux-машине (Р-Г1а): 3D-блок Solid N = 10⁴ … 3·10⁵ и сцена с нитями; время по стадиям (NVTX + Nsight Systems) на CPU (OpenMP, все ядра) и на GPU, в fp64 и fp32; таблица в отчёте. Замеры ГF показали, что на малых задачах CPU-шаг определяют накладные расходы конвейера, а не арифметика, — на GPU это нужно проверить в первую очередь.
- Кандидаты оптимизаций, каждая включается только при измеренном выигрыше и с повтором тестов Г4–Г10:
  1. режим `pull` для Solid-SPH (§3.4);
  2. переупорядочивание частиц Solid по ячейкам между шагами (кривая Мортона) для coalesced-доступа — с перенумерацией всего, что хранит индексы (монитор, вывод в исходном порядке);
  3. SoA-раскладка пулов вкладов, отдельный тонкий пул `dv` для контактов;
  4. одна синхронизация на шаг (буферы с запасом + флаг переполнения), затем CUDA Graph шага;
  5. перекрытие ветвей Solid и Fiber в разных потоках;
  6. смешанная точность: промежуточный вариант «координаты и накопители в `double`, парная арифметика во `float`». Раз основной режим — fp32 (Р-Г6), этот пункт важнее прочих оптимизаций для кейсов с пороговой физикой (BC6 с контактом типов 2–3). Решение о нём — по сверке с fp64 на этих кейсах. Приёмка — BC2 full и `e2e_3d_*` в тех же воротах, что у `double`.

## 5. Как сравнивать CPU и GPU

Побитное совпадение CPU и GPU **в общем случае недостижимо**: `pow/exp` в CUDA и в CRT MSVC отличаются на единицы ULP, компилятор CUDA по умолчанию сливает умножение со сложением (FMA), порядок primitives из поиска другой. Поэтому:

| Уровень | Что сравнивается | Допуск |
|---|---|---|
| Инфраструктура (Г3) | reduce на одинаковых primitives | побитно |
| Одна `SPH_HD`-функция | CPU vs GPU на случайных входах | ≤ 4 ULP без FMA; ≤ 1e-14 отн. с FMA |
| Множества пар/primitives | CPU vs GPU после сортировки | точное совпадение множеств |
| Один RHS (Г4, Г7, Г8) | все поля производных | fp64: ≤ 1e-12 отн. (с FMA), ≤ 1e-14 без FMA; fp32: ≤ 1e-5 отн. |
| K шагов | состояние частиц | допуски `test_regression` для N = K; при превышении — обоснованные GPU-допуски (Г5) |
| Физика | e2e-проверки и эталон BC2 | те же ворота, что у CPU |

Для разбора расхождений — сборка «строгий режим»: `-fmad=false` у `nvcc` (опция `SPH_CUDA_STRICT_FP`) и сортировка primitives по `(i, j)` на обоих backend; тогда расхождения сводятся к ULP библиотечных функций. Проверка тулчейна дала именно такой уровень: 4e-16 отн. в fp64 и 2e-7 в fp32 на `pow/exp/sqrt/log`. На другой карте (Р-Г1а) те же GPU-тесты обязаны пройти с теми же допусками.

Для fp32 все сравнения делаются парами одной точности: GPU fp32 против CPU fp32 (допуск уровня «один RHS» и сверок за 10–100 шагов в Г5–Г8 — **1e-5 отн.** вместо 1e-12, решение владельца 2026-09-27), регрессия GPU fp32 — против `tests/data/regression_fp32/`. Сравнение fp32 с fp64 — это измерение точности float, а не проверка корректности переноса; его числа — в FP32_REPORT.md.

GPU-путь детерминирован от запуска к запуску (Р-Г5): повторный прогон любого GPU-теста обязан давать побитно тот же результат — это отдельная проверка в каждом тесте `cuda`.
