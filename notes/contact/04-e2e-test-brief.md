## 1. Геометрия расчётной области (что именно переносить)

Блок `src/input.cpp:490-596` — осесимметричная (`axis_sim`, `dim = 2`) постановка
«ударник — керамика — керамика — окно», координаты `x[0] = r`, `x[1] = z`.

### 1.1 Параметры и опорные плоскости

```
delta_x = 0.0002            // шаг дискретизации, м
hsml    = 2.0 * delta_x     // для всех частиц
mass    = rho * delta_x^2   // плоская формула (закомментированы два осесимметричных варианта)

Z1 = 0.006
Z2 = Z1 + 0.003917 = 0.009917
Z3 = Z2 + 0.009033 = 0.018950
Z4 = Z3 + 0.025400 = 0.044350
```

### 1.2 Четыре слоя

| Слой | Материал | `itype` | ρ, кг/м³ | `vx[1]`, м/с | r, м | z, м |
|---|---|---|---|---|---|---|
| 1. Ударник | полиуретан 626 | 8 | 626 | **2210** | `0.5·dx … 0.04375` | `0 … 0.006` |
| 2. Керамика (летящая) | B4C | **10** | 2510 | **2210** | `0.5·dx … 0.0346` | `Z1+dx … Z2` |
| 3. Керамика (покоящаяся) | B4C | **10** | 2510 | 0 | `0.5·dx … 0.0346` | `Z2+4dx … Z3+4dx` |
| 4. Окно | LiF | 5 | 2638 | 0 | `0.5·dx … 0.0254` | `Z3+5dx … Z4+4dx` |

Общие для всех: `vx[0] = 0`, `u = 0`, `p = 0`, `rho_0 = rho`,
`axis[i] = true` при `fabs(r) <= 0.5·delta_x` (осевая колонка частиц).

Зазоры между слоями (`4dx` между 2 и 3, `dx` между 3 и 4) — **не артефакт**, а
физические границы раздела. Именно на них работают контактные силы.

Ожидаемое число частиц при `delta_x = 0.0002` — **≈ 34 163**
(6789 + 3287 + 7958 + 16129). `moni_particle = 12973` попадает в слой 3
(покоящуюся керамику) — это и есть точка, по которой снимается эталонная кривая.

### 1.3 Дефекты исходного блока — обязательны к исправлению при переносе

Блок закомментирован и с текущим API не компилируется. При переносе в тест:

- [ ] **Нет `sys.resize()`.** Блок пишет в `sys.x[0][ntotal]`, `sys.hsml[ntotal]` и т.д.,
      ни разу не обеспечив вместимость контейнера. В теле теста размер должен
      выделяться **до** заполнения: либо двухпроходно (сначала посчитать число частиц,
      потом `resize`), либо `resize` с запасом и усечение в конце. Двухпроходный
      вариант предпочтителен — он же даёт проверку §1.2 (ожидаемое число частиц).
- [ ] **`moni_particle = 12973;`** — обращение к глобалу, которого больше нет.
      Сейчас это `cfg.moni_particle` ([simulation_config.hpp](../../include/simulation_config.hpp)).
- [ ] **Накопление `r += delta_x` в условии `r <= 0.04375`** — число частиц зависит от
      ошибки округления double на границе. Перенести на целочисленный счётчик
      (`for (size_t ir = 0; ir < n_r; ++ir) { double r = (0.5 + ir) * dx; }`),
      иначе число частиц может «плавать» между компиляторами и платформами, и эталон
      перестанет совпадать. **Если это меняет число частиц относительно 34 163 —
      зафиксировать факт в отчёте и пересчитать эталон, а не подгонять условие.**
- [ ] `sys.axis` — `std::vector<char>` с bool-семантикой; присваивание `true` корректно,
      но требует предварительного `resize`.

### 1.4 Форма переноса

Геометрия оформляется как **функция в теле теста**, не как правка `input.cpp`:

```cpp
// test_e2e_bc2.cpp
// Геометрия кейса BC2, перенесённая из src/input.cpp:490-596 (закомментированный
// блок shock_tube). Здесь — единственный исполняемый экземпляр этой постановки.
struct Bc2Geometry { size_t ntotal; size_t moni_particle; double delta_x; };
Bc2Geometry build_bc2_geometry(ParticleSystem& sys, double delta_x);
```

`src/input.cpp` в рамках этого ТЗ **не меняется** — закомментированный блок остаётся
как есть. Если позже будет решено сделать геометрию частью продового кода, это
отдельная задача; дублирование фиксируется комментарием со ссылкой в обе стороны.

## 2. Блокер: `dim` — compile-time константа

[`param.hpp:8`](../../include/param.hpp#L8): `constexpr size_t dim = 1`. Кейс BC2 требует
`dim = 2` и `axis_sim = true`. Тест не может изменить это в рантайме.

**Решение E1 (нужен ответ владельца):**

| Вариант | Как | Цена |
|---|---|---|
| **A (рекомендуется)** | Сделать `dim` управляемым из CMake: `#ifndef SPH_DIM / #define SPH_DIM 1 / #endif`, `constexpr size_t dim = SPH_DIM;`. Цель `test_e2e_bc2` собирается с `-DSPH_DIM=2`, все остальные цели — без изменений (дефолт 1) | Затрагивает ADR-002 «dim как constexpr» — нужна приписка к ADR. Значение остаётся `constexpr`, семантика не меняется |
| B | Поменять `dim` на 2 глобально | Ломает текущий 1D-кейс ударной трубы и существующие тесты |
| C | Тест компилируется только при `dim == 2`, иначе `#if` — пустой `main()`, возвращающий «skipped» | Тест по умолчанию **никогда не выполняется** — иллюзия покрытия |

Без A тест либо не собирается, либо не выполняется. Это первое, что нужно сделать.

## 3. Конфигурация расчёта

Брать из `Керамика/Карбид бора/BC2/Initial_Conditions.txt` (ныне `cases/bc2/source/initial-conditions.txt`):

```
pa_sph = 2      nnps = 2      sle = 1      skf = 1
CFL = 0.1       epsilon = 0.25
alpha = 1.0     beta = 1.0    etq = 0.01
t_total = 3e-6  save_t = 2.5e-8   print_step = 50
```

- [ ] Файл в кодировке **cp1251** (комментарии нечитаемы как UTF-8). Тест **не должен**
      его парсить: значения задаются в коде теста явно, через `cfg.apply_defaults()` +
      присваивание полей. Путь к файлу указывается в комментарии как источник значений.
      Причина: парсинг зависел бы от рабочего каталога и от кодировки — обе вещи
      ломают тест непредсказуемо.
- [ ] `t_total = 3e-6` при `delta_x = 2e-4` даёт **≈ 730 шагов на ≈ 34 тыс. частиц** —
      это минуты, а не секунды (см. §5 о режимах).

## 4. Эталон и критерий расхождения

### 4.1 Что сравнивать

Продовый вывод — [`time_integration.cpp:304-305`](../../src/time_integration.cpp#L304-L305):

```cpp
file << time << " " << sys.vx[0][moni_particle] << " " << sys.itype[moni_particle];
```

Три колонки: `время  vx[0][moni]  itype[moni]`. Файлы `BC2/log_*.txt` — ровно этот
формат (число в имени = число частиц в прогоне: 100 … 10000).

**Расхождение, требующее решения (E2):** `log.txt` пишет `vx[0]` — **радиальную**
скорость. Эталонная кривая `BC2/BC2.txt` (154 строки, 2 колонки: время, значение)
лежит в диапазоне 160…820 м/с при скорости удара 2210 м/с и по смыслу похожа на
**осевую** скорость (`vx[1]`) свободной поверхности. В `log_*.txt` вторая колонка в
начале нулевая — что согласуется с радиальной скоростью на оси.

| Вариант | Что сравнивать |
|---|---|
| **A (рекомендуется)** | Сверять с `log_*.txt` (тот же столбец `vx[0]`, тот же генератор). `BC2.txt` не использовать — его происхождение и физический смысл не задокументированы |
| B | Сверять с `BC2.txt`, предварительно выяснив, какая это величина, и добавив её вывод в лог |

Принять решение **до** написания компаратора: от него зависит и формат эталона, и
тот факт, сравнивается ли расчёт с расчётом (регрессия) или с экспериментом (валидация).
Вариант A — регрессионный тест (ловит изменения поведения кода); вариант B —
валидационный (ловит расхождение с физикой). Это **разные тесты с разными допусками**,
и для CI нужен именно A.

### 4.2 Формат эталонного файла

Заготовка создана: [`tests/data/bc2_reference.txt`](../../tests/data/bc2_reference.txt).
Формат и порядок перегенерации описаны в её шапке.

### 4.3 Алгоритм сравнения

Шаг по времени адаптивный, поэтому временны́е сетки расчёта и эталона **не совпадают**.
Прямое построчное сравнение неприменимо.

- [ ] Обе кривые интерполируются линейно на общую равномерную сетку:
      `N = 200` узлов на `[t_min, t_max]`, где границы — пересечение диапазонов
      эталона и расчёта.
- [ ] Метрики:
  - `max_abs_dev` — максимальное абсолютное расхождение, м/с;
  - `rel_l2` — относительная норма L2: `||calc - ref||_2 / ||ref||_2`.
- [ ] Допуски (регрессионный режим, вариант A):
  - `rel_l2 < 1e-3` — жёсткий, ловит любое изменение численного поведения;
  - `max_abs_dev < 1.0` м/с — страховка от локальных выбросов.
  Для валидационного режима (вариант B) допуски заведомо другие (проценты, не 1e-3) —
  задаются владельцем после первого прогона, не угадываются.
- [ ] Диапазон времени эталона должен покрывать расчёт минимум на 80%; если
      пересечение меньше — тест падает с сообщением о несовпадении постановок,
      а не сравнивает огрызок.

### 4.4 Обязательные проверки помимо кривой

- [ ] Число частиц равно ожидаемому (§1.2) — ловит регрессию геометрии до того, как
      она проявится в кривой.
- [ ] Ни одного NaN/Inf в `x`, `vx`, `rho`, `p` на каждом сохранённом кадре.
- [ ] `rho > 0` и `mass > 0` для всех частиц на всех кадрах.
- [ ] Расчёт дошёл до `t_total`, а не оборвался раньше (шаг не сколлапсировал):
      число шагов конечно и меньше разумного потолка (например, 10× от ожидаемого).

## 6. Контактный сценарий — и найденная проблема

Кейс BC2 напрямую задевает решение **D2** из [02-decisions.md](02-decisions.md).

**Слои 2 и 3 — оба `itype = 10` (B4C о B4C).** Принятый критерий контактной пары
(`is_contact_pair`: `itype[i] != itype[j]`) **не обнаружит контакт между ними** —
летящая керамическая пластина и покоящаяся керамическая пластина для контактного
алгоритма невидимы друг для друга. При этом именно их соударение — физическая суть
кейса.

Следствия, которые ТЗ фиксирует, но не решает (решение за владельцем):

- [ ] Контактные сценарии теста (`contact_force_type = 1..3`) на BC2 покажут контакт
      **только** на границах ударник↔керамика (8↔10) и керамика↔окно (10↔5), но не
      на главной границе керамика↔керамика.
- [ ] Это **фактическое подтверждение** ограничения, заявленного при выборе D2=A,
      на реальном целевом кейсе — то есть аргумент в пользу перехода к D2=B
      (добавить идентификатор тела `body` в `ParticleSystem`).
- [ ] До перехода на D2=B тест **не должен** утверждать, что проверяет контакт
      керамика↔керамика. Лучше явная проверка-документация: тест фиксирует, что при
      `contact_force_type != 0` число контактных пар на границе слоёв 2/3 равно нулю,
      со ссылкой на это ограничение. Когда D2=B будет реализовано, тест меняет
      ожидание на ненулевое — и становится проверкой исправления.

Сценарии по типам сил (каждый — отдельный подтест, только в полном режиме):

| Сценарий | `contact_force_type` | Ожидание |
|---|---|---|
| Базовый | 0 | Совпадение с эталоном в пределах §4.3 |
| Контакт 1–3 | 1, 2, 3 | Без NaN; шаг не коллапсирует; `contact_max_delta` конечен; отдельный эталон **не требуется** — сверяется только устойчивость |

## 7. Технические требования к реализации

- [ ] Стиль теста — как в проекте: `int main()`, счётчик `failures`, `std::printf`,
      без фреймворка (образец — [`test_particle_system.cpp`](../../tests/test_particle_system.cpp)).
- [ ] Цель CMake по образцу `test_contact`; линкуются все модули конвейера
      (`src/*.cpp` кроме `main.cpp`) — вынести общий список исходников в переменную,
      чтобы не дублировать `file(GLOB)`.
- [ ] `time_integration()` пишет `log.txt` в **текущий каталог** жёстко зашитым именем.
      Тест обязан: работать во временном каталоге, либо удалять/переименовывать
      `log.txt` до и после прогона. Иначе тест затрёт лог реального расчёта
      пользователя. **Проверить это явно — тест не должен иметь побочных эффектов
      в рабочем каталоге разработчика.**
- [ ] Путь к эталону задаётся относительно каталога исходников через
      `target_compile_definitions(... SPH_TEST_DATA_DIR="${CMAKE_CURRENT_SOURCE_DIR}/tests/data")`,
      не относительно CWD.
- [ ] Вывод при падении: обе метрики (`rel_l2`, `max_abs_dev`), номер и время узла
      максимального расхождения, значения расчёта и эталона в этом узле. Без этого
      диагностировать расхождение по «FAIL» невозможно.

получается ровно `6789 + 3287 + 7958 + 16129 = 34163`, а правило выбора точки
монитора даёт ровно `moni_particle = 12973` — тот же индекс, что литерал
в оригинальном блоке. Разбор этого индекса: слой 3 начинается с 10076,
`n_z = 46`, значит `12973 = 10076 + 62·46 + 45` — тыльная поверхность
покоящейся керамики на радиусе `r = 62.5·dx = 0.0125 м`. Именно это правило
(последний узел по z, ближайший радиус к 0.0125 м) и закодировано, поэтому
точка монитора осмысленна при любом `delta_x`.

Smoke-режим (`delta_x = 8e-4`): `440 + 172 + 516 + 992 = 2120` частиц,
`moni_particle = 803`.

### Уточнения и решения, принятые при реализации

1. **Начальный шаг по времени.** `main.cpp` ставит `dt = 0.005` из ветки
   `shocktube` — это одномерная ударная труба, к BC2 отношения не имеющая.
   Тест берёт начальный `dt` из `compute_cfl_timestep()` — того же критерия,
   которым конвейер пересчитывает шаг дальше.
2. **Регистрация полного режима.** CTest не умеет «тест зарегистрирован, но по
   умолчанию не запускается»: голая метка `LABELS "slow"` из §5 оставила бы
   многоминутный прогон в обычном `ctest`. Поэтому регистрация гейтится опцией
   сборки: `cmake -S . -B build -DSPH_E2E_SLOW_TESTS=ON`, затем
   `ctest --test-dir build -L slow`. Метка `slow` сохранена.
3. **Проверка кадров.** `time_integration()` не даёт хуков на каждый кадр,
   поэтому §4.4 проверяется по файлам `sph_output_*.txt`, которые конвейер
   пишет сам — во временный каталог прогона.
4. **Smoke-сверка кривой вырождена.** При `t_total = 3e-7` слои 2 и 3 ещё не
   сомкнулись (зазор `4·delta_x = 3.2 мм` при скорости 2210 м/с закрывается за
   ≈ 1.4·10⁻⁶ с), поэтому `vx[0][moni]` тождественно нулевой, и сверка кривой
   в smoke-режиме ничего не ловит. Тест печатает об этом явное предупреждение.
   Smoke по §5 и предназначен только для «геометрия строится, конвейер не
   падает, нет NaN, шаг не коллапсирует» — эти проверки работают. Ловить
   регрессию по величине способен только полный режим.
5. **Отношение к D4.** [02-decisions.md](02-decisions.md) D4 рекомендовал
   вариант A (не вводить `dim` как параметр сборки). E1 = A — это ровно
   вариант D4=B; решение пересмотрено владельцем, ADR-002 дополнен.
6. **`--keep-workdir`.** Флаг сверх ТЗ: не удалять временный каталог прогона.
   Без него обрыв полного прогона невозможно разобрать — `log.txt` и кадры
   удаляются вместе с каталогом.

### Что тест нашёл: полный режим до `t_total` НЕ доходит

Первое, что обнаружил тест на реальной постановке, — **полный режим ни разу
не дошёл до `t_total`**. Четыре прогона (`delta_x = 2e-4`, `t_total = 3e-6`,
`contact_force_type = 0`, macOS / Apple Clang, 7 потоков OpenMP) дали два
разных исхода, оба — отказ:

| Прогон | Исход | Где |
|---|---|---|
| 1 | `int_force: некорректная частица 18169 (rho = -446, itype = 5)` | слой 4, `ir = 1` |
| 2 | `int_force: некорректная частица 24 (rho = -2650, itype = 8)` | слой 1, `ir = 0` (осевой столбец), шаг 735, `t = 1.30e-6` (43 % расчёта) |
| 3 | `int_force: некорректная частица 10122 (rho = -6825, itype = 10)` | слой 3, `ir = 1`, шаг 850, `t = 1.59e-6` (53 %) |
| 4 | **коллапс шага по времени**, расчёт не заканчивается | `dt` упал с `2.20e-9` до `1.0e-11` (в 110 раз) начиная с шага ~688; на шаге 2769 время всё ещё `1.24e-6` (41 %) — прогон снят вручную |

Два факта, важные для ТЗ:

**1. Все отказавшие частицы стоят на оси или в соседнем столбце** (`ir = 0`
или `ir = 1`, то есть `r = 0.5·dx` и `1.5·dx`). Это указывает на осевую
особенность `1/r`, а не на контактную часть (контакт в этих прогонах выключен).

**2. Расчёт не воспроизводим от прогона к прогону.** Сравнение `log.txt`
двух прогонов одного и того же бинарника:

| Шаг | `t`, с | прогон A, м/с | прогон B, м/с | разность |
|---|---|---|---|---|
| 474 | 8.0e-7 | совпадают бит-в-бит | | 0 |
| 475 | 8.0e-7 | 4.00335 | 4.00336 | ~1 ulp |
| 500 | 8.4e-7 | 8.86446 | 8.86447 | 1e-5 |
| 600 | 1.02e-6 | 78.1263 | 78.1259 | 4e-4 |
| 700 | 1.25e-6 | 245.717 | 188.482 | **57.2** |
| 849 | 1.59e-6 | 274.156 | 145.79 | **128** |

Расхождение рождается на уровне младшего разряда (порядок суммирования в
`link_list` задаётся `#pragma omp atomic capture` и меняется от прогона к
прогону) и за ~200 шагов вырастает до десятков м/с, то есть до 20-50 %.

Отсюда прямое следствие: **допуски §4.3 (`rel_l2 < 1e-3`, `max_abs_dev < 1 м/с`)
в полном режиме недостижимы при текущем коде** — не из-за регрессии, а потому
что два прогона одного и того же бинарника расходятся сильнее допуска. Пока
расчёт неустойчив, полный регрессионный эталон бессмыслен: он не отличит
изменение кода от перестановки потоков.

Прямое следствие для ТЗ: **§8 п.5 (генерация полного эталона) невыполним**.
Это ровно та ситуация, ради которой п.5 и требует сначала признать расчёт
корректным: эталон, снятый с обрывающегося и невоспроизводимого расчёта,
закрепил бы ошибку. Тест сообщает, на каком шаге и в какой момент времени
произошёл обрыв, а также первый и минимальный `dt` за прогон.

**Гипотеза о причине (требует проверки владельцем, в объём ТЗ не входит).**
В `density.cpp` осесимметричная поправка
континуитета добавляется **внутри цикла по парам**:

```cpp
if (axis_sim == true && dim == 2)
{
    double ax_i = (pvx[0][i] / px[0][i]);
    Acc::add(drhodt[i], (-(ax_i)));   // ни массы соседа, ни ядра — и на КАЖДУЮ пару
}
```

В отличие от соседних осесимметричных членов в
[`int_force.cpp`](../../src/int_force.cpp#L417-L430) (`pmass[j] * ... * w[k]` —
нормальная SPH-сумма) и от закомментированных строк прямо над ним, этот член
не взвешен ни массой, ни ядром, а применяется по одному разу на каждую пару
с участием частицы. При ~25-50 соседях он оказывается умножен на число соседей.
Правильная форма источника — `-rho_i * vx[0][i] / x[0][i]` **один раз на
частицу** (ср. одномерную ветку в
[`time_integration.cpp`](../../src/time_integration.cpp#L124)). Частицы у оси
(`x[0] = 0.5·dx`) получают наибольший вклад — именно там и растёт ошибка.

**Смежное наблюдение.** Механизм зеркальных частиц для оси не работает:
вызов `virt_part(...)` в [`single_step.cpp`](../../src/single_step.cpp#L103-L106)
закомментирован, причём с сигнатурой на четыре аргумента, тогда как объявление
в `virt_part.hpp` — на три; то есть блок в
текущем виде не компилируется. При `axis_sim = true, dim = 2` осевой столбец
частиц остаётся без симметричных соседей.

Ни то, ни другое тест не чинит: это правки физического ядра, выходящие за
рамки ТЗ (и за рамки решений D1-D6, E1-E3).
