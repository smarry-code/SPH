## 2. Архитектура

### 2.1. Общая схема

До внедрения частицы твёрдого тела (Solid) хранились в одном массиве структур `ParticleSystem`, а расчёт шага устраивался как последовательность процедур (`direct_find`/`linked_list` → `density` → `int_force` → `art_visc` → `av_vel` → `ext_force`), которые находили пары соседей и сразу же, тут же в цикле, суммировали в общие массивы производных — с раскраской графа пар (`PairGraph`) или атомарными операциями, чтобы разные потоки не писали в одну ячейку одновременно.

После внедрения расчёт устроен как конвейер с явным разделением стадий, без атомарных операций и без раскраски графа вообще:

```
Поиск соседей (SpatialIndex)
        │
        ▼
Построение primitives (пары/сегменты/тройки частиц, только чтение состояния)
        │
        ▼
Kernel: вычисляет вклад каждого primitive, пишет в свой thread-local буфер
        │
        ▼
Reduce: вклады раскладываются по шардам и суммируются (owner-computes)
        │
        ▼
Finalize: производные величины дописываются финальными по-частичными членами
        │
        ▼
ODESolver: шаг предиктор-корректора или Эйлера
        │
        ▼
Postprocessing: возврат на поверхность текучести (Мизес/JH-2), пересчёт h, разрыв связей нитей
        │
        ▼
Вывод кадра
```

Это в точности архитектура, описанная в постановке [`notes/fiber-model/fiber-problem-statement.md`](fiber-problem-statement.md) (разделы «CPU executor», «Search», «Compute interaction kernel», «Reduce»). Она нужна не только твёрдому телу — ровно та же схема, без каких-либо исключений, используется для всех пяти типов взаимодействий, включая три новых, связанных с нитями.

Два "compute-структуры" (в терминах плана) — это Solid (`ParticleSystem`, как и раньше) и Fiber (новый `fiber::FiberState`+`fiber::FiberTopology`). У каждой свой тип накопителя вклада (`SolidDelta`, `FiberDelta`), но обе проходят через один и тот же механизм поиска/сборки/суммирования.

### 2.2. Пять типов взаимодействий

| # | Взаимодействие | Файл | Что делает | Куда идёт вклад |
|---|---|---|---|---|
| 1 | `Solid-SPH` | [`include/interactions/solid_sph.hpp`](../../include/interactions/solid_sph.hpp) | Обычная гидродинамика SPH: неразрывность, импульс, искусственная вязкость, деформации, закон Гука, XSPH, зеркальные частицы у оси | `SolidDelta` → Solid |
| 2 | `Solid-Solid-Contact` | [`include/interactions/solid_contact.hpp`](../../include/interactions/solid_contact.hpp) | Штрафной контакт частиц разных тел (типы 1–3 по ADR-007: pinball, Swegle, импульсный) | `SolidDelta` → Solid |
| 3 | `Fiber-Bond` | [`include/interactions/fiber_bond.hpp`](../../include/interactions/fiber_bond.hpp) | Сила растяжения связи внутри нити (только растяжение, без изгиба) | `FiberDelta` → Fiber |
| 4 | `Fiber-Fiber-Contact` | [`include/interactions/fiber_contact.hpp`](../../include/interactions/fiber_contact.hpp) | Пространственный контакт бусин **разных** нитей (Герц, 4 геометрических случая) | `FiberDelta` → Fiber (обе нити) |
| 5 | `Fiber-Solid-Contact` | [`include/interactions/fiber_solid_contact.hpp`](../../include/interactions/fiber_solid_contact.hpp) | Контакт сегмента нити с частицей твёрдого тела | `FiberDelta` → Fiber, **и** `SolidDelta` → Solid |

Каждый файл — самостоятельный модуль: primitive (какие частицы участвуют и что уже вычислено при поиске), kernel (сама физика, только чтение состояния), функция для `dt_limit` (ограничение шага по времени от этого типа взаимодействия) и, где нужно, диагностика.

### 2.3. Как устроен контакт — подробно

Это отдельный вопрос, потому что в проекте теперь **четыре разных вида контакта**, и они умышленно устроены по одному образцу.

**Solid-Solid-Contact** (существовал и раньше, теперь просто переехал на новую схему без изменения формул, [`include/contact_force.hpp`](../../include/contact_force.hpp) с математикой не тронут). Пара частиц разных тел (`body[i] != body[j]`, поле `body` — это номер тела, у существующих генераторов равно `itype`, у входного k-файла — PID) даёт проникновение `p = R_i + R_j - r`, где `R` — эффективный радиус частицы `R = ½(m/max(ρ,ρ₀))^{1/dim}`. При `p > 0` есть контакт, сила считается одним из трёх штрафных законов (`contact_force_type` в конфигурации), прикладывается вдоль нормали к обеим частицам с противоположным знаком.

**Fiber-Bond** — не контакт в пространственном смысле, а сила внутри самой нити, между топологическими соседями (по `prev`/`next`). Только растяжение: `F = EA·max(l/l0 - 1, 0)·n`. Разрыв (Ф7) — отдельное правило Postprocessing, не часть этой силы.

**Fiber-Fiber-Contact** — механический контакт бусин **разных** нитей (`object_id[i] != object_id[j]`). Устроен сложнее Solid-Solid, потому что нить — это не облако частиц, а цепочка с осью, и Meyer (источник метода) намеренно не прикладывает силу bead-to-bead, чтобы нити не цеплялись за промежутки между бусинами. Вместо этого по соседям каждой бусины восстанавливается локальное направление нити (`p_i`, `p_j`), и в зависимости от того, концевая бусина или внутренняя, применяется одна из четырёх геометрических формул (Surface-Surface — обе внутренние, Surface-End/End-Surface — одна на конце, End-End — обе на конце). Дальше вычисляется зазор `D`, при `D < d` (диаметр нити) — сила Герца, и она распределяется не только на исходную пару бусин, но и на их соседей по нити (`i_prev`/`i_next`), пропорционально тому, где на сегменте на самом деле лежит точка контакта. У почти параллельных нитей система вырождается (`|p_i × p_j| < ε`), и код переключается на формулу Surface-End.

**Fiber-Solid-Contact** — контакт сегмента нити (двух соседних бусин `a`, `b`) с одной частицей твёрдого тела `s`. Ближайшая точка на сегменте `q = a + λ(b-a)`, `λ` зажимается в `[0,1]`. Сила Герца, коэффициент жёсткости `K_fs` — обобщение формулы Meyer на **разные** материалы (нить/твёрдое тело) через классическую механику Герца: `1/E* = (1-ν_f²)/E_f + (1-ν_s²)/E_s`. Модуль Юнга и коэффициент Пуассона твёрдого тела не были параметрами материала — их вывели из уже существующих `K` (модуль объёмного сжатия) и `G` (модуль сдвига) по формулам `E = 9KG/(3K+G)`, `ν = (3K-2G)/(2(3K+G))` — это новая функция `elastic_by_itype()` в [`include/materials.hpp`](../../include/materials.hpp). Важная деталь реализации: пара `(бусина f, частица s)` рождает сегмент `(f, next(f))`, то есть только **один** сегмент на бусину, а `λ` принимается в полуинтервале `[0,1)`, кроме последнего сегмента нити — это защита от двойного учёта силы в узле, где сходятся два сегмента.

Все четыре вида контакта используют одну и ту же инфраструктуру поиска (`rhs::SpatialIndex`) и одну и ту же схему вкладов (`ContributionWriter` → `reduce_contributions`) — отличаются только primitive и формулы внутри kernel.

### 2.4. Инфраструктура (`include/rhs/`)

Написана первой (этап Ф1) и переиспользуется всеми пятью типами взаимодействий, физики в ней нет:

- **`cpu_executor.hpp`** — `CpuExecutor`: `parallel_for`/`parallel_reduce`/`parallel_scan`/`parallel_sort` поверх OpenMP, с детерминированным режимом (фиксированный порядок суммирования независимо от числа потоков);
- **`spatial_index.hpp`** — `SpatialIndex<Dim>`: поиск пар по сетке, с фильтром «свой/чужой тип», замена `FlatGrid`+`linked_list`;
- **`contributions.hpp`** — `ContributionWriter`, `ContributionBuffer`, `reduce_contributions()`: каждый поток пишет вклады в свой буфер, затем один проход раскладывает их по шардам и суммирует — без атомарных операций и без раскраски графа;
- **`rhs_workspace.hpp`**, **`types.hpp`** — вспомогательные типы.

### 2.5. Postprocessing и ODESolver (этапы Ф7–Ф8)

**Postprocessing** ([`include/interactions/postprocessing.hpp`](../../include/interactions/postprocessing.hpp)) выполняется строго после шага решателя, в две фазы: поиск событий (параллельно, только чтение) и применение (последовательно). Два вида событий: возврат девиатора на поверхность текучести (Мизес/JH-2 — эти вызовы просто вынесены из двух копий в общую функцию, физика не менялась) и разрыв связи нити (`l > l_break`) — с переприсвоением `object_id` оторвавшейся части и увеличением `topology_version`.

**ODESolver** ([`include/ode/ode_solver.hpp`](../../include/ode/ode_solver.hpp)) — два явных решателя с одинаковым интерфейсом: `PredictorCorrectorSolver` (рабочий, ровно та схема, что была в проекте: один RHS на шаг, предиктор на полшага по прошлой производной, корректор от сохранённых значений) и `EulerSolver` (эталонный для тестов сходимости, явный первый порядок, без XSPH). Выбирается ключом `ode_solver` в конфигурации, по умолчанию — PredictorCorrector. Именно на этом этапе исчезло дублирование: раньше `time_integration()` для обычного расчёта (`ParticleSystem&`) и для расчёта с нитями (`fiber::Model&`) были двумя независимыми копиями одного и того же цикла; теперь обе — тонкие обёртки над одной внутренней функцией, шаблонной по типу решателя.

## 4. Тестирование

### 4.1. Регрессия (14)

[`tests/test_regression.cpp`](../../tests/test_regression.cpp) считает кейс с нуля ровно N шагов (останов по числу шагов, а не по времени — чтобы при чуть разошедшемся dt сравнивались состояния после одинакового числа шагов). Затем все поля всех частиц сверяются с эталоном из `tests/data/regression/` по относительным нормам. Две контрольные точки — два независимых прогона:
- **N = 1:** одно вычисление RHS и один шаг решателя, допуск тесный. Это и есть стенд «эквивалентность RHS на одном состоянии» для этапа Ф4.
- **N = K:** накопление за много шагов (контакт, JH-2, Мизес, h, XSPH), допуск шире.

Состав: `regression_bc2_contact0..3` и `regression_bc6_contact0..3` (осесимметричный 2D), `regression_bc2mini3d_contact0..3` (уменьшенный BC2 в 3D) — по одному тесту на тип контакта. Плюс `regression_selfcheck` и `regression_selfcheck_3d` — проверка самого механизма сравнения. Эталон генерирует этот же тест (`cmake --build build --target regression_golden`, при `OMP_NUM_THREADS=1`); ни один зарегистрированный тест в дерево исходников не пишет.

### 4.4. Как тесты проверяют физический смысл

Тесты взаимодействий проверяют не только формулу, но и её физический смысл: третий закон Ньютона (сумма сил по всем участникам одного primitive равна нулю), предельный переход (формула для разных материалов при одинаковых даёт формулу Meyer для одинаковых нитей), порядок сходимости решателя. В нескольких случаях ревью проверяло тест на то, что он вообще способен поймать ошибку: временно портило знак или формулу в коде, убеждалось, что тест падает, и возвращало код обратно.

### 4.5. Пробелы в покрытии

- **Продовый `time_integration` ни разу не запускается с непустыми нитями.** Динамические тесты нитей (№6, 10, 11, 12Б) используют либо локальные драйверы, повторяющие формулы предиктор-корректора, либо решатель напрямую. Продовый цикл вызывается только с пустыми нитями (№12А, 13). Порядок вызовов RHS нитей внутри цикла и сложение Fiber-вкладов с Solid-вкладами тестами не проверяются.
- **У нового модуля Solid-Solid-Contact нет собственного модульного теста.** [`include/interactions/solid_contact.hpp`](../../include/interactions/solid_contact.hpp) покрыт только регрессией и сквозными тестами. `contact_test` проверяет старый `ext_force`, который из продового цикла больше не вызывается.
- **Слабая проверка в `fiber_bond_test`:** третий закон Ньютона записан как `mi*dv0 + mj*dv1 < 1e-6` без модуля ([`tests/test_fiber_bond.cpp`](../../tests/test_fiber_bond.cpp), `test_force_formula`) и пройдёт при любом отрицательном дисбалансе. Сейчас это не опасно: соседние проверки сверяют ускорение каждой бусины с формулой до 1e-9.
- **Широкие допуски:** 20 % на скорость волны в нити и порог 5·E₀ на энергию PredictorCorrector заметно шире остальных проверок. Они отделяют верное поведение от грубо неверного, но не поймают ошибку в несколько процентов.

## 6. Известные ограничения (осознанно оставлены, не баги)

- **Радиус поиска Fiber-Fiber/Fiber-Solid не учитывает растяжение нити сверх номинальной длины связи.** Радиус берётся как максимум *недеформированной* длины связи `l0` по всем материалам. При сильном растяжении (близко к разрыву) контакт у стыка двух сегментов теоретически может быть пропущен поиском. Для текущих тестов деформации малы, риск не проявляется; наивное исправление (взять `l_break` вместо `l0`) признано на ревью опасным — в некоторых тестах `l_break` намеренно выставлен в 10⁹ раз больше `l0` как сигнал «никогда не рвать», и это раздуло бы радиус поиска до брутфорса.
- **`sle = 2`** (альтернативный метод пересчёта длины сглаживания, использующий дивергенцию скорости по соседям) не реализован на новом пути — бросает исключение с понятным сообщением. Ни один существующий конфигурационный файл его не использует (везде `sle = 1`).
- **Шим совместимости**: `prochnost_cem_JH2` (модель повреждения JH-2) по-прежнему читает `sxx`/`exx`/`rxy` и т.п. из `ParticleSystem` напрямую, а не как явные параметры — решение принято на Ф7 сознательно, ради нулевого риска для регрессии. Комментарий у `SolidDelta`/`SolidFinal` (`include/interactions/solid_sph.hpp`) явно предупреждает: если этот шим когда-нибудь будут убирать, `prochnost_cem_JH2` нужно менять вместе с ним, не по отдельности.

## 8. Трение между нитями (Fiber-Fiber-Contact)

### 8.1. Модель

Реализовано динамическое сухое трение Кулона **без памяти контакта** — по спецификации [`notes/fiber-contact/fiber-friction-implementation.md`](../fiber-contact/fiber-friction-implementation.md) (следует читать целиком для полного вывода; здесь — сжатое изложение того, что реально попало в код).

Скорость точки контакта на каждой стороне строится теми же весами и теми же топологическими соседями, что уже использует распределение нормальной силы Герца (`w_i`/сосед `i_n` и симметрично для `j`):

```
v_c,i = w_i * v_i + (1 - w_i) * v_(i_n)
v_c,j = w_j * v_j + (1 - w_j) * v_(j_n)
```

Для концевой бусины без соседа (`w = 1`) формула вырождается в `v_c = v_end` — отдельного случая в коде нет. Относительная скорость `v_rel = v_c,i − v_c,j` раскладывается на нормальную и тангенциальную составляющие по нормали контакта `n`, и при `|v_t| > eps_v` сила трения

```
F_t = −μN · v_t / |v_t|
```

(на вторую нить — `−F_t`), при `|v_t| ≤ eps_v` — `F_t = 0`. Итоговая сила `F = N·n + F_t` распределяется по бусинам ровно теми же весами, что и одна только нормальная составляющая — отдельного распределения для трения нет. Нормальный закон Герца (геометрия, `D`, `n`, `N`) не тронут буквально.

Правило смешения коэффициентов трения `μ_ff` двух материалов вынесено в отдельную функцию `fiber_friction_coefficient` (`include/interactions/fiber_contact.hpp`): для одинаковых материалов возвращается точное `μ_ff` (без `std::sqrt`, чтобы `mu_ff == mu_ff` не портилось округлением), иначе — `μ_ij = sqrt(μ_i · μ_j)`. Порог `eps_v` — константа `kFiberContactFrictionMinVt = 1e-8` м/с, нужна только для защиты от деления на ноль. `dt_limit` контакта (`compute_fiber_contact_dt_limit`) трением не затрагивается: у закона Кулона нет собственной жёсткости, характерное время трения не даёт более жёсткого ограничения, чем уже посчитанное по нормальному контакту Герца.

> **Пометка.** Описание `w_i`/соседа `i_n` выше и весь этот раздел 8 в целом
> относятся к геометрии Fiber-Fiber-Contact, действовавшей на момент
> внедрения трения (primitive = пара бусин с топологическими соседями,
> несколько primitives на одно пересечение). После перехода на схему «пара
> сегментов — одна сила» (`notes/fiber-contact/fiber-contact-segment-pairs.md`,
> `include/interactions/fiber_contact.hpp`) скорость точки контакта и сама
> сила трения распределяются весами `(1-s, s)` на стороне A и `(1-t, t)` на
> стороне B (параметры ближайшей точки на сегменте), а не `w_i`/`(1-w_i)`
> по топологическим соседям; на одно физическое пересечение нитей теперь
> приходится ровно один контакт (кроме «седла» изогнутой нити — тогда два,
> и это разные точки, не дубликат). Закон трения Кулона (§8.1 выше) при этом
> не изменился, изменилась только геометрия, на которой он считается.
> Отдельный раздел 9 про переход на пары сегментов добавляется отдельно.

### 8.2. Параметр материала

Новое поле `mu_ff` (`double`, по умолчанию `0.0`) в `FiberMaterial` (`include/fiber/fiber_system.hpp`) — намеренно последнее в структуре, чтобы агрегатная инициализация существующих мест в коде и тестах не сломалась. Во входном файле нити (`src/fiber_input.cpp`) `mu_ff` — необязательное **седьмое** поле блока `MATERIAL`: при отсутствии сохраняется старое 6-полевое поведение (`mu_ff = 0`), при наличии — читается и валидируется (отрицательное или нечисловое значение — ошибка формата, исключение).

### 8.3. Гарантия побитной регрессии при mu = 0

Инвариант, вынесенный в заголовок `fiber_contact.hpp` как жёсткое требование: **`mu_ff = 0` обязан давать побитово то же поведение, что и до внедрения трения**. Это обеспечено буквально, а не приближённо — нормальные выражения (геометрия, вес, сила Герца) оставлены без изменений, блок вычисления трения физически не выполняется, если `mu == 0` (проверка стоит до вызова `coulomb_friction_force`, а не полагается на то, что `F_t` посчитается и окажется нулём). Именно это проверяет `test_friction_zero_mu_regression`, и это же подтверждено независимо — побитным сравнением демо (§8.6).

### 8.4. Тестовый интегратор test_e2e_fiber_contact.cpp

Локальный интегратор сценарного теста переведён на порядок боевого цикла PredictorCorrector (предиктор с `dt_prev` → RHS → новый `dt` → корректор) вместо прежнего упрощённого порядка. Это понадобилось потому, что трение — в отличие от нормальной силы Герца — зависит от скорости бусин в момент вычисления RHS, и порядок «предиктор/корректор относительно RHS» стал значимым для результата, а не только для точности интегрирования.

### 8.8. Открытый вопрос — дребезг при малой относительной скорости

Диагностический прогон (c) — `mu = 0.2`, `v_t0 = 0.05` м/с — показывает, что относительная тангенциальная скорость центральных бусин **меняет знак каждые 1–2 шага** (6 смен знака за прогон), с максимальной амплитудой после первой смены знака **0.086 м/с** — что **больше** самой стартовой `v_t0 = 0.05` м/с. Для сравнения: при `mu = 0` та же величина за тот же прогон меняется лишь на ~5·10⁻⁴ м/с (см. §8.6, сценарий a).

Причина — прямое следствие того, что реализована именно явная схема Кулона без памяти состояния (без stick/slip): при малой `|v_t|` направление `v_t/|v_t|` на каждом шаге пересчитывается заново по текущему знаку, и сила трения может «перебрасывать» тангенциальную скорость через ноль, а не гасить её к нулю. Амплитуда дребезга, превышающая исходную скорость скольжения, — признак того, что в этом режиме явная схема может нефизично закачивать энергию в касательное движение, а не только её рассеивать.

Это осознанный и задокументированный (в шапке `fiber_contact.hpp`, п. 4) риск базовой реализации, не регрессия и не баг относительно спецификации первого варианта — сама спецификация явно ограничивается «трением без памяти» и оставляет регуляризацию около `v_t = 0` вне рамок первой итерации. Кандидаты для следующей задачи (перечислены в спецификации, §13):
- ограничение `|F_t| ≤ m_red·|v_t|/dt` (без памяти, простая отсечка по доступному за шаг импульсу);
- полноценный stick/slip с тангенциальной пружиной (память состояния контакта, накопленное тангенциальное смещение).

## 10. Fiber-Solid-Contact: владение узлом и радиус по текущей длине

Постановка — `notes/fiber-contact/fiber-solid-contact-fix.md`; реализация — `include/interactions/fiber_solid_contact.hpp`, `include/interactions/fiber_contact_common.hpp`; тесты — `tests/test_fiber_solid.cpp`, сценарные — `tests/test_e2e_fiber_solid.cpp`. Задача исправляет две ошибки, обе вызванные неполнотой исходного контакта нить–твёрдое тело.

### 10.1. Что изменено

**Правило владения узлом** (таблица из спецификации §1):

| условие (после прижатия параметра t) | решение |
|---|---|
| 0 < t < 1 | контакт, λ = t |
| t ≥ 1, последний сегмент | контакт, λ = 1 |
| t ≥ 1, не последний сегмент | пропуск (узел b принадлежит следующему сегменту) |
| t ≤ 0, первый сегмент | контакт, λ = 0 |
| t ≤ 0, не первый сегмент | вычислить t_prev для сегмента (prev(a), a); t_prev ≥ 1 → контакт, λ = 0; иначе пропуск |

**Константа прижатия** `kFiberContactSnapEta = 1e-9` (общая с Fiber-Fiber-Contact, `include/interactions/fiber_contact_common.hpp`):
- `if (t > 1.0 - η) t = std::max(t, 1.0);`
- `if (t < η) t = std::min(t, 0.0);`

Значения строго за пределами [0,1] сохраняются; прижимаются только значения у самих границ.

**Функция `fiber_solid_segment_param`** — единственная точка вычисления параметра t проекции Solid-частицы на сегмент нити. Используется и для собственного сегмента (a, b), и для соседнего (prev(a), a) при проверке правила владения узлом. Обеспечивает побитовую воспроизводимость и независимость правила от округления.

**Структура `FiberSolidContactPrimitive`**: поле `bool a_is_first` заменено на `long long a_prev` (индекс prev(a), −1 для первой бусины). Нужен сам индекс для вызова `fiber_solid_segment_param` на соседнем сегменте при проверке владения узлом.

**Радиус поиска** `r_f,max + r_s,max^contact + L_max`, где **L_max — текущая** (не номинальная l_0) максимальная длина связи:
```
L_max = max_bonds |x_i - x_j|
```
вычисляется `exec.parallel_reduce` по `topology.bonds` функцией `fiber_max_current_bond_length` (`include/interactions/fiber_contact_common.hpp`, общая с Fiber-Fiber-Contact). Связи работают только на растяжение и рвутся лишь в Postprocessing после шага, поэтому внутри шага сегмент может быть длиннее l_0, и номинальное l_0 как оценка радиуса не годится. Контакт у дальнего конца растянутого сегмента может выпасть из поиска при использовании l_0.

**Документация обновлена** в `notes/fiber-model/fiber-problem-statement.md` (раздел Fiber-Solid-Contact, новый подраздел «Постановка проекта: владение узлом» с таблицей правила) и в `notes/fiber-model/fiber-plan.md` (таблица рисков, строка о потере контакта во внешнем секторе излома закрыта).

## 11. Трение нить–нить как проекция на уровне скоростей

Постановка — `notes/fiber-contact/fiber-friction-projection.md`; реализация — `include/interactions/fiber_friction.hpp` (шапка); интерфейс решателя — `include/ode/ode_solver.hpp` (`FiberVelocityUpdate`, `fiber_velocity_update`, `fiber_coeff`); стадия трения — `src/time_integration.cpp` (после шага `dt`, перед `advance`); слоты — `include/interactions/fiber_contact.hpp` (`FiberFrictionContact`). Тесты: `tests/test_fiber_friction.cpp`, `tests/test_ode_solver.cpp` (8.9), `tests/test_e2e_fiber_contact.cpp`. Разбор дребезга: `notes/fiber-contact/friction-chattering-analysis.md`, раздел «После исправления».

Архитектурное отличие от трения в разделе 8: там трение было в RHS, здесь оно вынесено в отдельную стадию между шагом на `Δt` и `advance()`. Это позволяет применить проекцию на уровне скоростей (метод Ньютона для трения с прилипанием) без изменения порядка RHS и без добавления осциллирующих членов в гидродинамику Solid.

### 11.1. Что изменено

**Архитектура трения:**
- Kernel нормального контакта (`compute_fiber_contact_geometry`) считает только нормаль и заполняет слоты `FiberFrictionContact` (по одному на примитив контакта, слот содержит индексы бусин, нормаль, коэффициент трения);
- при `mu_ff = 0` стадия трения не выполняется (пропуск блока вычислений, не полагаться на обнуление силы);
- интерфейс решателя `fiber_velocity_update` с параметрами:
  - `base` — начальное значение скорости (для PC: на полшаге шаг 1, на целом шаге далее);
  - `h` — шаг интегрирования (для PC: `dt/2`, затем `dt`; для Эйлера: `dt`);
  - возвращает `base + h·dv` побитно;
- приватный метод решателя `fiber_coeff(dt)` (и `fiber_use_base()`) — единственное место, где задаются коэффициент `h` и база обновления скорости: им пользуются и `correct_fiber`/`step_fiber`, и `fiber_velocity_update`;
- импульс трения в `friction_projection_impulse`:
  ```
  J = min(μN·h, ‖u_t‖/W),   W = Σ_A c_k·α_k²/m_k + Σ_B c_k·β_k²/m_k
  ```
  где `W` — обратная эффективная масса точки контакта с учётом mass splitting (`c_k` — число активных контактов бусины `k`);
- удалены из кода: `coulomb_friction_force`, `kFiberContactFrictionMinVt` (заменены на встроенные проверки);
- введена константа `kFiberFrictionInteractionType = 4` (метка `interaction_type` вкладов трения нить–нить в домене `FiberDelta`).

**Отступление от спецификации — mass splitting:**
Спецификация `notes/fiber-contact/fiber-friction-projection.md` не содержит `mass splitting`, однако в сценарии медленного скольжения (раздел 11.3, сценарий d) узел со множественными контактами (например, «седло» на пологом изломе) давал двойное перекомпенсирование прилипания, и трение неправильно перебрасывало касательную скорость. По решению пользователя `mass splitting` перенесён сюда из задачи 4: в эффективной массе точки контакта `1/m_k` заменяется на `c_k/m_k`: `W = Σ_k c_k·α_k²/m_k` (по бусинам обеих сторон), где `c_k` — число активных контактов с ненулевым весом у бусины `k` на этом шаге. Без этого остаток тангенциальной скорости при прилипании изменялся вдвое в зависимости от числа слотов на узле.

### 11.6. Открытые вопросы

**1. «Седло» на пологом изломе:** два контакта в почти одной точке с разными нормалями приводят к остатку трения ≈ `|u_n|·|Δn|` (см. критерий (1) в 11.3). На узле со множественными слотами прилипание происходит по каждому слоту независимо, но остаток не обнуляется полностью. Указано в `fiber-plan.md` как риск; требует либо явного обнуления по тангенциальному направлению одной из нормалей, либо перехода к парам сегментов с единственной нормалью контакта.

**2. Недокомпенсирование mass splitting:** в узлах со многими контактами, когда число активных примитивов меняется от шага к шагу, `mass splitting` усредняет эффективную массу по включённым контактам. Точное решение требует итераций (implicit scheme), не реализовано в явной схеме.

**3. Проекция в многостадийных решателях (RK-4):** текущая реализация подразумевает двухстадийный PC или одностадийный Эйлер. Для RK-4 неясно, на каком этапе рунге-кутты применять проекцию, чтобы не потерять консервативность импульса; не решено.

### 12.3. Решения по критериям (приняты пользователем)

Диагностика сцены (c) показала, что критерии спецификации §7.2 (c) в части «нить прилипает за один шаг» не выполняются принципиально, и их заменили.

1. **Релаксация вместо мгновенного прилипания.** Критерий «`‖u_t‖ ≤ 1e-9·v_t0` сразу после первого шага прилипания» заменён на релаксацию за конечное время: `T_relax` = **6.05·10⁻⁵ с** (`dt`, 23 шага) и **5.84·10⁻⁵ с** (`dt/5`, 111 шагов); отношение **1.036** ≤ 1.2 (время релаксации не зависит от шага, как и должно быть для физического процесса). После `T_relax` — `‖u_t‖ ≤ 1e-9·v_t0`.
2. **Допуски от `v_t0` в фазе прилипания.** Рост `‖u_t‖` за шаг ≤ **1 %** `v_t0` (факт 0.21 % при `dt`, 0.085 % при `dt/5`); перескок проекции ≥ **−5 %** `v_t0` (факт −2.3 % и −1.7 %). Это ограничение одного прохода Якоби при связанных контактах на общих бусинах с неравномерной `u_t`. Проверенные и отвергнутые гипотезы: веса `c_k` (варианты `Σα/α` и `Σα²/α²` не помогают, первый ломает тест mass splitting); появление новых контактов; несовместные нормали; дефект реализации. Даже 30 развёрток Гаусса–Зейделя не дают `1e-9·v_t0` — остаток связан со структурой связанных контактов, а не с неточностью одного прохода. Точное решение — итерации (дальнейшая работа).
3. **Бусина одновременно в контактах нить–нить и нить–Solid при разных массах партнёров:** перекомпенсация **0.18 %** (без splitting — 103 %), допуск **1 %**. Mass splitting по счёту контактов точен только при равных массах партнёров — известное ограничение.
4. **Геометрия e2e.** Старт нити сдвинут по `x` на `−v_t0·t_подхода`, зазор 0.5 мм (иначе при `v_t0 = 2` м/с нить уходит с пластины до касания). Сцена (c) дополнительно прогнана в геометрии со сдвигом по `y` на 0.75 мм (вертикальные нормали); в исходной геометрии нить лежит над швом между рядами частиц, нормали наклонены, и критерии на `‖u_t‖` неприменимы.
