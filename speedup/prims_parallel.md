# Сборка примитивов Solid-SPH: параллельная запись по индексам (B1)

Дата замеров: 2026-10-03/04.

- **Исходное состояние:** ветка `speedup` @ `06e0b99`, итоговая версия
  [reduce_targets.md](reduce_targets.md) (код `59a3576`).
- **Исправление:** ветка `speedup-prims`, коммиты `eef7086`, `75ba0d0`, `5712ace`, `526794d`.

Стенд, сборки и случаи — как в [base.md](base.md) §2:
- сервер `claude-compute` — виртуальная машина, 8 vCPU;
- g++ 15.2, libgomp, `-O2`;
- аппаратных счётчиков нет.

## 1. Итог

- **Причина.** После параллельного поиска пар главный поток в одиночку собирал примитивы по
  1.2 млн пар: 34 мс при любом числе потоков, 27 % шага A на 8 потоках.
- **Исправление.**
  - Сборка стала параллельной по схеме «подсчёт → префиксная сумма → запись по индексам».
  - Тип ядра сглаживания выбирается один раз вне цикла.
  - Сами ядра не встраиваются: встраивание замедляло цикл, проверено замером (§6.4).
  - Порядок и содержимое `primitives`, `real_pairs`, `contact_pairs` прежние при любом числе
    потоков.
- **Корректность.**
  - 74/74 теста.
  - Побайтное совпадение при `OMP_NUM_THREADS=1` в трёх сценариях.
  - ASan и UBSan без ошибок при 1, 2 и 8 потоках.
  - Независимое ревью ошибок не нашло (§4).
- **Память** (§5).
  - Page faults и системных вызовов `mmap`/`munmap`/`brk` на шаг нет — как и до правки.
  - RSS на плато и не вырос.
  - Настройка `malloc` время не меняет.
  - Гонок за кэш-линии не видно: запись масштабируется в 7.5 раза на 8 потоках.
- **Сборка примитивов** (A, мс/шаг, опыт T):

  | Потоки | было | стало |
  |---|---|---|
  | 1 | 35.3 | 35.9 (подсчёт 2.6 + запись 33.3) |
  | 8 | 35.2 | **4.9** (подсчёт 0.45 + запись 4.4) |

- **Шаг продуктовой сборки** (100 шагов, медиана трёх прогонов, опыт M):

  | Случай | 1 поток, с/шаг | изменение | 8 потоков, с/шаг | изменение |
  |---|---|---|---|---|
  | A | 0.540 → 0.545 | +0.9 % (в пределах разброса) | 0.139 → **0.112** | **−19.5 %** |
  | 1T_A | 0.606 → 0.605 | −0.1 % | 0.164 → **0.133** | **−18.9 %** |
  | 1T | 0.0853 → 0.0855 | +0.2 % | 0.0220¹ → **0.0189** | **−14 %** |

  ¹ base для 1T на 8 потоках взят из предыдущей серии M: в итоговой серии base попал в
  «медленный режим» (0.0338), см. §6.5.

  По опыту T шаг A на 8 потоках — 127.7 → 97.2 мс (**−23.9 %**). S(8) для A выросло с 3.88 до
  4.85, подгонка по Амдалу даёт f = 0.15 → 0.09.
- **Загрузка** A на 8 потоках: простой ядер (`mpstat`) 41 % → 23 %, доля последовательного кода
  главного потока в профиле 43 % → 21 %.
- **Попутная находка** (§6.5): старый последовательный цикл чувствителен к раскладке стека.
  Тот же бинарник base при одной длине аргумента `--out` шёл на 25 % медленнее. Это исказило
  одну из серий M здесь и, вероятно, точку base A на 8 потоках в
  [reduce_targets.md](reduce_targets.md). Новая параллельная сборка такой чувствительности
  не показывает.

## 2. Гипотеза B1 и её симптомы

Гипотеза сформулирована по итогам B2 ([reduce_targets.md](reduce_targets.md) §7, N1).
После параллельного поиска пар главный поток в одиночку проходил цикл по всем 1.2 млн пар
в `build_solid_sph_search`. На каждую пару:
1. заново считались `dx`, `r2`, `sqrt(r2)`;
2. вызывалась `kernel()` из отдельной единицы трансляции, с ветвлением по `skf`;
3. делался `push_back` 40-байтного `SolidSphPrimitive`;
4. делался `emplace_back` в `real_pairs`;
5. для межтельных пар — `push_back` в `contact_pairs`.

Рабочие потоки всё это время ждали.

Симптомы (A, 8 потоков, до исправления):

| Симптом | Значение |
|---|---|
| Время сборки | 34 мс при 1, 2, 4 и 8 потоках |
| Доля в шаге | 6.5 % на 1 потоке, 27 % на 8 |
| Профиль главного потока | `kernel()` — 11.1 %, `push_back` — 6.4 % |
| Простой ядер (`mpstat`) | 40 % |
| Спин libgomp у рабочих | 14 % |

Гипотеза **подтверждена**: на 8 потоках сборка ускорилась в 7.2 раза, а шаг сократился почти
на её прежнее время (§6.2).

## 3. Исправление

| Коммит | Файл | Изменение |
|---|---|---|
| `eef7086` | `include/kernel.hpp`, `src/kernel.cpp` | Тело `kernel()` перенесено в заголовок **дословно**, тремя функциями `kernel_cubic/gauss/quintic`. `kernel(int skf, …)` остался переключателем с прежней сигнатурой. В `build_solid_sph_search` `skf` выбирается один раз до цикла, вызов ядра — прямой |
| `75ba0d0` | `include/interactions/solid_sph.hpp`, тесты | Параллельная сборка по индексам — см. ниже |
| `5712ace` | там же | По независимому ревью: границы блока вычисляются до цикла; эталон теста считается дословной копией прежнего ядра (`06e0b99:src/kernel.cpp`), так что тест проверяет и дословность переноса; добавлен случай `skf = 0` |
| `526794d` | `include/kernel.hpp` | Ядра помечены `[[gnu::noinline]]`: встраивание замедляло проход записи на ~20 % (§6.4). Код ядер и порядок вычислений не меняются |

**Сборка по индексам (`75ba0d0`).**
1. Пары делятся на `nb = clamp(n / 2048, 1, 8 · потоков)` непрерывных блоков.
2. **Проход 1** (`parallel_for` по блокам) считает в каждом блоке число примитивов, пар
   `real_pairs` и пар `contact_pairs` тем же предикатом, что прежний цикл.
3. **Префиксная сумма** по блокам (последовательно, не больше 64 элементов) даёт смещения.
4. `primitives`, `real_pairs`, `contact_pairs` получают размер через `resize()`.
   `clear()` в начале функции убран: иначе `resize()` каждый шаг заново обнулял бы около
   67 МБ на главном потоке. Буферы живут в `SolidStepWorkspace` и переиспользуются; на
   ранних выходах массивы обнуляются через `resize(0)`, ёмкость сохраняется.
5. **Проход 2** (`parallel_for` по блокам) пишет элементы по своим смещениям. Тело — прежняя
   логика, `k` в `contact_pairs` — глобальный индекс в `real_pairs`, как прежний
   `real_pairs.size()`.
6. Счётчики блоков — `struct alignas(64) SolidBlockCount`, по кэш-линии на блок, как
   `LocalPairs` в `spatial_index.hpp`. Вектор лежит в `SolidSphSearchResult` и
   переиспользуется.

Позиция элемента задаётся номером пары, а не блоком или потоком. Поэтому массивы совпадают с
прежней последовательной сборкой при любом числе потоков.

**Что намеренно не сделано.**
- Двойной `sqrt` (в `accept` и в цикле) оставлен. Убрать его можно, только храня `r` для
  каждой пары (+10 МБ) или сравнивая `r2 < R²`, а второе может изменить набор пар на границе
  радиуса из-за округления.
- `real_pairs` (копия пар real-real, 19 МБ) оставлен: его читает `test_sph_body_isolation`,
  а `k` из `contact_pairs` уходит в `meta` вкладов контакта. Теперь он пишется параллельно.

**Тесты.**
- `test_sph_body_isolation`:
  - `test_parallel_build` — решётка 2×8³ (77 тыс. пар, 37 блоков). `skf` = 0, 1, 2, 3, изоляция
    тел вкл./выкл., 1/2/7 потоков. Сравнение с последовательным эталоном (копия прежнего цикла
    и прежнего ядра) — `primitives` через `memcmp`, `real_pairs` и `contact_pairs`, включая
    `k`.
  - `test_build_memory` — повторные вызовы в один `SolidSphSearchResult` на сценах 8, 8, 8, 10,
    6, 8, 10. `data()` и `capacity()` всех четырёх буферов не меняются, пока размер не
    превышает достигнутый максимум; `blocks.data()` кратен 64.
- `test_axisym` (сцена с призраками): результат при 1 и 7 потоках равен последовательной
  сборке по тем же парам.

## 5. Память

Проверки — по образцу [memory.md](memory.md) и [base.md](base.md), `~/perf_bench_v9/mem/`.
Сборки base (`59a3576`) и `5712ace`; правка `526794d` меняет только атрибут встраивания ядер и
память не трогает.

**Page faults на шаг** (`perf stat`): разность прогонов на 400 и 100 шагов, делённая на 300.

| Случай | base | после правки |
|---|---|---|
| A, 1 поток | 0 | 0 |
| A, 8 потоков | 0 | 0 |
| 1T_A, 8 потоков | 28.6 | 25.6 |

Все ≈ 0.39 млн page faults приходятся на подготовку сцены и нулевой шаг. В 1T_A остаток —
путь Fiber, правка его не касается.

**Системные вызовы памяти** (`strace -f -c`, A, 8 потоков; точки трассировки syscalls на
сервере закрыты):

| Сборка | `mmap` | `munmap` | `brk` | `madvise` |
|---|---|---|---|---|
| base, 100 / 400 шагов | 130 / 129 | 104 / 104 | 61 / 66 | 7 / 7 |
| после правки, 100 / 400 шагов | 129 / 129 | 104 / 104 | 66 / 66 | 7 / 7 |

На шаг — 0 у обеих сборок: постоянных выделений и освобождений нет.

**RSS во времени** (`/proc/<pid>/status` раз в секунду, 400 шагов). После нулевого шага
`VmRSS` выходит на плато и не растёт: A на 8 потоках — 1455 МБ, как у base; пик `VmHWM`
совпадает (A 1452/1455 МБ, 1T_A 1506 МБ). Max RSS в опыте M одинаков во всех точках.

**Контроль с настройкой malloc** (`MALLOC_MMAP_MAX_=0 MALLOC_TRIM_THRESHOLD_=68719476736
MALLOC_TOP_PAD_=268435456`, A, 100 шагов, 3 повтора):

| Потоки | без настройки | с настройкой |
|---|---|---|
| 8 | 0.1134 [0.1111–0.1157] | 0.1147 [0.1146–0.1147] |
| 1 | 0.583 [0.575–0.584] | 0.563 [0.553–0.588] |

Разница в пределах разброса — аллокатор не участвует.

**Выравнивание и кэш-линии.**
- Адреса буферов (инструментированная сборка, первый шаг): `blocks` выровнен по 64 Б;
  `primitives` и `real_pairs` — со смещением 16 Б от начала кэш-линии (обычное выравнивание
  `malloc`), `contact_pairs` — 16–48 Б.
- Счётчики блоков пишутся каждым потоком в свою кэш-линию.
- На выходных массивах соседние блоки делят не больше одной кэш-линии на границу: меньше
  64 линий на массив, только в момент записи. Выравнивать позиции на выходе нельзя — они
  зависят от подсчёта.
- Косвенная проверка: проход записи масштабируется почти идеально — 33.3 → 17.3 → 8.8 →
  4.4 мс на 1/2/4/8 потоках (7.5×). Провала, характерного для борьбы за кэш-линии, нет.
  `perf c2c` недоступен: на ВМ нет счётчиков PMU.

### 6.4. Встраивание ядра: проверка гипотезы

В первой версии (`5712ace`) ядро встраивалось в цикл. Серия M показала +1.0…+1.4 % на одном
потоке во всех трёх случаях, а T — что сам проход записи (39.6 мс) медленнее старого
последовательного цикла (34.9 мс).

Две проверки (A, 30 шагов, 3 повтора, инструментированные сборки, `~/perf_bench_v9/X`, `Z`):

| Вариант прохода записи | 1 поток, мс | 8 потоков, мс |
|---|---|---|
| старый последовательный цикл (весь) | 33.7–35.3 | 34.0–34.7 |
| ядро встроено (`5712ace`) | 39.7–40.8 | 5.2 |
| + локальные копии указателей и скаляров (`prims-v2`) | 38.7–40.3 | 5.1 |
| ядро `[[gnu::noinline]]` (`526794d`) | **33.0–34.0** | **4.4** |

- **Гипотеза алиасинга** (захваты по ссылке перечитываются после каждой записи) почти не
  подтвердилась: −1 мс. Правка не взята.
- **Гипотеза встраивания подтверждена:** с вызовом ядра проход записи на 6.7 мс быстрее на
  одном потоке и на 0.8 мс — на восьми. Вероятные механизмы — нехватка регистров в теле цикла
  с встроенным ядром (3–4 деления и с десяток живых значений) и раскладка более длинного
  тела цикла. Без счётчиков PMU это не разделить.
- Гипотеза о кэше (проход подсчёта вытесняет пары, которые старый цикл читал сразу после
  склейки) не проверялась: объём правок (однопроходная ветка или подсчёт внутри
  `parallel_merge`) превышает возможный выигрыш — около 2.5 мс на одном потоке. Остаток
  +0.6 мс сборки на одном потоке приходится на проход подсчёта.

### 6.5. Чувствительность старого цикла к раскладке стека

В серии M для `5712ace` base A на 8 потоках дал 0.167–0.179 с/шаг, хотя тот же бинарник в
серии v8 давал 0.141–0.145, а в прогонах под `perf stat` и `strace` — 0.145–0.148. У новой
сборки таких колебаний нет.

**Контроль** (A, 8 потоков, 100 шагов, `~/perf_bench_v9/C`, `Y`):

| Запуск base | с/шаг | user, с |
|---|---|---|
| обычный, имя каталога `base_A_8_rN.out` (15 символов) | 0.162–0.178 | 84–96 |
| то же под `perf stat` | 0.145–0.148 | 68–70 |
| обычный, длина `--out` 1, 3, …, 13, 17, …, 23 символа | 0.135–0.146 | 65–69 |
| обычный, длина `--out` **15** символов | **0.177–0.179** | **94** |
| итоговая сборка, любая длина | 0.110–0.115 | ~67 |

- **Режим определяется раскладкой стека:** длина аргументов сдвигает стек главного потока.
  В медленном режиме user растёт на ~25 мс × 8 потоков на шаг — замедляется последовательный
  участок, а рабочие потоки всё это время крутятся в ожидании.
- **Старый последовательный цикл чувствителен к этому, параллельная сборка — нет.**
- **В итоговой серии M** у обеих сборок метки одинаковой длины. Base A на 8 потоках попал в
  нормальный режим (0.139), зато base 1T на 4 и 8 потоках — в медленный (§6.1, сноска ²).
- **Следствие для [reduce_targets.md](reduce_targets.md).** Там base A на 8 потоках
  (0.172 с/шаг, каталог `base_A_8_rN.out`, 15 символов) почти наверняка снят в медленном
  режиме. Выигрыш B2 на 8 потоках по M (−16 %) завышен. Опыт T из того отчёта (156.1 →
  125.8 мс) этим не затронут.

## 9. Ограничения

- **Аппаратных счётчиков нет.** Механизм замедления встроенного ядра (§6.4) и чувствительность
  к раскладке стека (§6.5) установлены опытами, а не по счётчикам.
- **Раскладка стека влияет на base.** Сравнения на 8 потоках сверены с прогонами base в
  нормальном режиме (опыты T, C, Y); там, где base попал в медленный режим, это отмечено.
- **Опыт T снят по одному прогону** на точку. Значимы различия больше 3–5 %.
- **Свёртка на одном потоке** колеблется между процессами (§6.2): выигрыши шага на одном потоке
  меньше 3 % не засчитываются.
- **Проверки памяти** сделаны для `5712ace`; `526794d` отличается только атрибутом встраивания
  ядер.
